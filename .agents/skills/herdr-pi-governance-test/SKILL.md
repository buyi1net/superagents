# Herdr Pi 治理回归

## 职责

把一次治理规则回归从本地变更推进到可审计结果：发布指定规则，确认 GitHub 与 Pi 缓存处于同一提交，使用用户确认的真实项目题启动两路全新 Pi 会话，等待主动完成通知，最后只读核验真实产物。

本 skill 只编排完整流程，不保存 Herdr 操作细节和出题细则，也不替被测 Agent 修复、清理或补齐测试项目。它位于 `.agents/skills/`，只供本仓库维护使用，不属于 `skills/` 正式发布源。

## 必须读取的项目说明

- 设计、修改、复核或准备发送题目时，先完整读取[治理测试出题原则](../../../docs/治理测试/出题原则.md)。题面未取得用户明确确认前，不得派发。
- 执行测试目录核验、pane 管理、模型启动、题目派发、静默等待、结果读取或 Herdr 失败恢复前，先完整读取[Herdr 治理测试操作说明](../../../docs/治理测试/Herdr操作说明.md)。

两份项目说明分别是出题和 Herdr 操作的直接来源。本文件只负责调用顺序，不复制其中的注意事项；说明发生变化时只维护对应文档。

## 开始条件

开始前收集并记录：

1. 目标分支和本轮需要发布的规则文件；
2. [Herdr 治理测试操作说明](../../../docs/治理测试/Herdr操作说明.md)记录的默认模型和 thinking 等级，或用户当次明确指定的新配置；
3. 用户预先提供的两个独立测试根绝对路径；
4. 两个本轮唯一的 pane 或 Agent 名称；
5. 一份按出题原则生成、完成 Management 全范围覆盖核对并经过用户确认的完整题面。

缺少任一项时只补齐当前缺口，不猜测路径、模型、旧题或用户授权。启动前读取 `git status --short --branch` 和实际 diff，保留不属于本轮的用户改动。

## 执行流程

1. 按[治理测试出题原则](../../../docs/治理测试/出题原则.md)生成新题和 Management 覆盖表，向用户明确区分“发送给考生的题面”与“不发送的覆盖表”，等待用户确认。
2. 只提交并推送用户指定的本轮规则文件，核对本地提交与远端分支 SHA。
3. 通过 Pi 正式更新入口拉取插件，核对实际缓存提交和本轮规则文件内容。
4. 按[Herdr 治理测试操作说明](../../../docs/治理测试/Herdr操作说明.md)核验测试根、建立或复用右侧上下 pane、启动两路全新 Pi 会话并派发已确认原文。
5. 确认两路均已送达并开始工作后结束当前轮次，按操作说明静默等待主动完成事件。
6. 收到结果后只读核验两路磁盘产物、运行证据和项目外副作用，不修改被测项目。
7. 汇总版本、模型、派发、产物和验证证据，报告差异及未确认项。

## 发布规则

按用户指定分支操作，以下以 `main` 为例。

1. 阅读 diff，确认根入口、地图链接、治理规则和项目级 skill 的改动范围；执行仓库当前确实存在的校验。没有真实结果时不得声称测试通过。
2. 只暂存本轮目标文件，不带入无关用户改动、测试项目、缓存、日志或生成物。

   ```bash
   git status --short
   git add <本轮目标文件>
   git commit -m "<中文变更说明>"
   git push origin main
   ```

3. 记录并比较本地与远端 SHA：

   ```bash
   local_sha="$(git rev-parse HEAD)"
   remote_sha="$(git ls-remote origin refs/heads/main | awk '{print $1}')"
   test "$local_sha" = "$remote_sha"
   ```

远端 SHA 不一致时停止后续同步结论，不强推或重写历史。

## 拉取并验证 Pi

1. 使用 Pi 的正式更新入口：

   ```bash
   pi update --all
   pi list --approve
   ```

2. 从 `pi list --approve` 的实际输出取得 `git:github.com/buyi1net/superagents` 缓存路径，不使用旧路径或 pane 顺序推测。
3. 核对缓存提交与本地发布提交：

   ```bash
   pi_cache="<pi list 输出的实际缓存路径>"
   test "$(git -C "$pi_cache" rev-parse HEAD)" = "$local_sha"
   git -C "$pi_cache" log -1 --oneline
   ```

4. 至少比较一份本轮规则文件在源仓库与缓存中的内容：

   ```bash
   rule_file="<本轮目标规则文件>"
   git -C "$pi_cache" show HEAD:"$rule_file" | sha256sum
   git show "$local_sha":"$rule_file" | sha256sum
   ```

任何 SHA 或内容不一致都标记为同步失败，不启动依赖最新规则的测试。Pi 在进程启动时读取插件内容，因此必须先同步，再启动两个全新会话；旧会话不能证明新规则已经载入。

## 结果审计

收到两路主动完成事件后，按 Herdr 操作说明读取最终回报，并对磁盘事实进行只读检查：

- 与开考前初始目录记录比较，区分用户预置内容与本轮产物；
- 核对项目入口、目录边界、文档链接、源码、测试、构建、运行和交付证据；
- 按本轮治理场景检查对应规则是否自然生效；
- 检查进程、端口、服务、计划任务、环境变量、全局安装等项目外副作用；
- 分开记录“规则明确要求”“规则没有覆盖”“Agent 自行决策”“Agent 自述”和“证据不足”。

测试参考材料治理时，额外检查分类、索引、参考说明、本地副本、来源版本、许可证和 Git 边界；不得只根据 Agent 自述判断完成情况。

## 交付报告

报告至少包含：

1. 规则源仓库提交 SHA、GitHub 远端 SHA、Pi 缓存路径和缓存 SHA；
2. 两个 pane 与 Agent 的名称、ID、模型、thinking 等级和测试根；
3. 用户确认的题面原文和两次 `agent_prompted` 送达证据；
4. 两路 `done` 或 `blocked` 结果及实际测试、构建和磁盘证据；
5. 入口、目录治理、运行数据、交付物和项目外副作用的发现；
6. 两路相同点、差异点、失败项和仍未确认的证据。

不得把“推送成功”写成“项目质量通过”，不得把 Agent 声称写成磁盘事实，也不得在未获授权时修复测试项目或删除测试产物。

## 非 Herdr 异常

- Git 提交、推送或远端 SHA 校验失败：保留现场，停止同步后的步骤并报告，不强推、不重写历史。
- `pi update --all` 失败或缓存 SHA 不一致：报告实际缓存状态，不使用旧缓存冒充新规则。
- 出题、测试目录、pane、派发、等待和 Herdr 恢复相关异常：回到对应项目说明执行，不在本文件另建第二套处理规则。
