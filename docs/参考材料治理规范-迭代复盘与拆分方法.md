## 一、复盘结论

以 Git 中可以核验的版本为准，[参考材料治理规范](../skills/constitution/management/reference.md) 共形成 11 个正式版本：初稿 1 个，后续修订 10 次。

- 初稿：106 行；
- 定稿：229 行；
- 累计变动：新增 606 行，删除 376 行，共改动 982 行；
- 截至复盘时已发布的定稿提交：`82f88236af49ed502b9f471f1b5fb48d1a67df3d`；
- 未提交的手工试稿和定稿后的手工调整没有独立快照，不计入正式版本次数。

这些数字只能说明改了多少，不能证明修改方法正确。前期多次修改是根据最终产物猜测模型为什么跑偏，再用新条款修补表面现象，工程效率很低，其中一些改动还制造了新的问题。

本轮真正得到的结论是：

> 制度由人制定和拍板。AI 不得根据异常产物猜测制度意图并自行增删规则。凡因模型行为准备修改制度，必须先检查该模型执行时可取得的原始会话上下文、实际加载规则和工具记录，证明“规则原文—模型理解—最终行为”的因果关系。人类确定处理方向后，AI 负责润色、查漏补缺、冲突检查和回归验证。

测试只能暴露行为、证伪假设和验证一次明确修改是否产生预期效果，不能替人决定制度应该是什么，也不能证明一份制度对所有模型和未来场景都完整可靠。

### 第 2 次修订：`9d7912f`

### 第 5 次修订：`3678eca`

## 三、前期迭代为什么低效

### 1. 从结果猜原因

看到目录不对就增加目录规则，看到 AGENTS 缺章节就增加强制语气，看到模型照抄就继续限制示例。多数时候没有先证明模型加载了什么、如何理解规则以及哪句话触发了行为。

异常产物只能证明结果有问题，不能单独证明原因。根据产物直接补规则，很容易修错层级。

### 2. 把模型执行错误和制度错误混在一起

本轮出现过不同性质的问题：

- 触发条件没有命中；
- 会话加载了旧规则；
- 模型受到错误文件污染；
- 规则表达存在歧义；
- 两条规则共同推出错误结果；
- 模型看到了正确规则但漏执行；
- 底层 Git 机制理解错误；
- 测试题提前泄露了答案。

这些问题不能都通过扩充 `reference.md` 解决。在哪一层发生，就只能在哪一层修。

### 3. 把更多约束误认为更可靠

当原因没有确定时，增加条款只会压缩模型自由度，不一定改善制度。版本控制章节一度为了隔离项目治理文件和来源仓库，要求建立额外边界，最后反而制造了 `archive/` 多层目录。

规则越强，错误规则造成的偏差越稳定。

### 4. 误用测试

测试提示词最初过于像考试，模型可以从“整理资料”“治理测试”“读取规则”等表达猜出预期答案。后来又一度把不同模型交叉验证当作可靠性来源。

全新 Agent 同样会从不了解项目开始执行；得到人类纠正后，它又拥有了额外上下文，不能继续代表零上下文接手者。换更多 Agent 只是增加样本，不能把模型变成制度认证者。

### 5. 正确看待前几次提交

前几次提交留下了失败样本，也完成了适用范围、人机入口、生命周期等必要结构调整，但不能把整个过程包装成推荐的迭代方法。按工程效率判断，其中相当一部分属于没有查明原因之前的症状修补。

真正的正确演进始于第一次检查 DeepSeek 的执行上下文，并确认它根本没有加载参考材料治理规则。以后复用的是从那一刻开始的根因分析方法，不是“发现异常就继续补条款”的修改次数。

## 四、真正的转折：先发现 DeepSeek 没有加载规则

### 第一次上下文检查：规则没有进入会话

DeepSeek 已经拉取了外部资料，却没有按参考材料场景建立目录、入口和长期维护方法。即使用户提醒“太乱了”并要求处理，它仍然没有把任务识别成参考材料治理。

只看结果，可以继续猜测它没有理解治理目标、提示词不够明显，或者 `reference.md` 正文缺少强制要求。但检查它当时可取得的执行上下文后，首先确认的是：DeepSeek 根本没有加载参考材料治理规则。

这意味着当时无论怎样修改 `reference.md` 正文，都不会影响 DeepSeek 的行为。问题位于上层触发和路由，不在场景规范内容。

随后调整的是 skill 主文件中的触发条件：按外部材料在项目中的实际用途识别场景，不依赖用户是否说出“参考资料”“整理”或其他特定词，并要求在确定存放位置或开始处理前加载规范。

这是本轮第一次真正按根因修改：

`异常结果 → 检查原始上下文 → 确认规则未加载 → 修改触发和路由`

从这里开始，测试不再只是观察产物好不好，而是先确认模型实际收到了什么规则，再决定应该改哪一层。

### 第二次上下文检查：规则已经加载，但规则本身有问题

后续测试中，DeepSeek 创建了类似下面的目录：

`D:\260813-D\reference\核心依据\silero-vad\archive`

只看磁盘结果，很容易认为它没有理解目录规范、擅自增加层级或命名能力不足。

再次检查 DeepSeek 当时可取得的会话上下文后，确认了三件事：

1. 它已经加载并阅读了最新参考材料治理规则；
2. 它没有忽略版本控制制度；
3. 它认为项目治理文件和来源仓库必须处于不同版本控制边界，因此需要用额外目录隔离来源工作树。

当时规则还同时要求参考说明和本地存档位于同一个参考项文件夹。为了同时满足这些要求，建立 `archive/` 是能够从规则推出的合理行为。

DeepSeek 不是没有遵守规则，而是把错误的规则执行得很认真。问题在制度设计，不在模型自觉性。

进一步核验 Git 的实际机制后确认：

- 文件位于来源工作树，不等于会被自动提交；
- 未跟踪文件可以写入来源仓库自己的 `.git/info/exclude`；
- 不需要用额外目录隔离参考说明；
- 也不需要修改上游 `.gitignore`。

因此，正确修复是由人重新确定版本控制边界，再由 AI 帮助把决定写清楚，而不是继续猜测 DeepSeek 为什么“乱建目录”。

这次形成了第二条因果链：

`异常结果 → 检查原始上下文 → 确认规则已经加载 → 找到导致行为的具体条款 → 由人修改制度`

### 两次检查共同说明了什么

模型上下文的作用不是让 AI 替人决定规则，而是提供根因证据。必须建立下面的因果链：

`实际规则版本 → 模型读取内容 → 模型采用的判断 → 工具操作 → 磁盘结果`

任何一环缺失，都只能称为假设。无法取得原始上下文时，可以列出可能原因和补充证据需求，但不得把猜测直接写进正式制度。

第一次检查证明“没有加载规则时不能改正文”，第二次检查证明“加载规则也不代表模型错，可能是制度本身把它带向错误结果”。这两次才构成本轮真正值得复用的演进方法。

## 五、AGENTS.md 问题的真实结论

### 1. 为什么让模型自由编写不可靠

执行任务的 Agent 必须先理解项目。理解过程会把项目状态、用户刚刚确认的决定、本次命令和全局规则带入上下文。随后让同一个 Agent 编写供未来接手者使用的 `AGENTS.md`，会产生结构性偏差：

- 省略它认为已经显而易见的内容；
- 假定后续 Agent 也知道当前对话和全局规则；
- 因当前不适用而删除未来需要的条件规则；
- 把本次命令、工具和临时状态写成长期要求；
- 自查时利用自身上下文补全文档没有写出的含义。

这不是换一个更强模型就能稳定解决的问题。

### 2. 为什么换全新 Agent 也不能认证

全新 Agent 可以暴露一份 AGENTS 的缺口，但不能证明它完整。人类一旦纠正它，它就不再是零上下文接手者；继续换新 Agent 也只是在有限任务上重复抽样。

因此：

- 新 Agent 失败，可以证明某个问题存在；
- 新 Agent 通过，只能证明这次任务没有暴露问题；
- Agent 之间不能互相授予制度定稿资格；
- 测试结果必须交给人解释和决策。

### 3. 最终文件为什么开始落实

后期测试中的 AGENTS 逐渐完整，不代表模型已经学会自主编写长期制度，而是人把可自由决定的范围收窄了：

- 明确 README、AGENTS、CLAUDE 的职责；
- 由人确定必须具备的维护章节；
- 明确示例是能力下限；
- 禁止按当前状态删除条件规则；
- 已有项目约束只做局部修补；
- 把维护结果验收写进项目入口；
- 由全局执行者回读实际文件。

模型此时主要负责把人已经确定的维护契约落到项目，而不是自行决定契约内容。

### 4. AGENTS.md 应当是什么

`AGENTS.md` 不是当前 Agent 对项目理解的自由总结，也不是保证未来可以完全无人接手的万能手册。它是由人类和上层制度控制的项目维护入口，只保存：

1. 上层制度已经确定的长期维护能力；
2. 可以从磁盘重新核验的稳定入口和事实；
3. 人类明确拍板的项目专用约束；
4. 遇到未覆盖判断时的停止和求助边界。

更现实的“可交接”目标是：后续 Agent 能在既定范围内安全开始，不重复已知错误；遇到制度没有覆盖的新判断时，能够识别边界并交还人类决定。

## 六、人和 AI 的职责边界

### 人负责

- 确定制度要解决的问题和最终效果；
- 决定治理对象、职责边界、取舍和例外；
- 判断一次异常是模型漏执行，还是制度本身有问题；
- 决定哪些项目约束需要长期保留；
- 批准规则修改和最终定稿。

### AI 负责

- 收集并整理可取得的原始会话上下文、规则版本、工具记录和磁盘证据；
- 还原规则与行为之间的因果关系；
- 区分路由、版本、表达、冲突、工具机制和执行问题；
- 在人确定方向后润色文字、查漏补缺、消除歧义和检查冲突；
- 执行经人确认的修改；
- 验证发布版本、缓存和具体行为是否符合人的决定。

### AI 不负责

- 根据异常产物猜测用户真正想要的制度；
- 自行把一次模型行为上升为通用规则；
- 自行决定长期制度中哪些内容可以删除；
- 用另一个 Agent 的意见代替人的判断；
- 根据若干测试通过宣布制度完整、完美或永远可靠。

### 测试 Agent 负责

测试 Agent 只是产生行为样本。它的回复、工具记录和磁盘产物都是证据，不是制度意见；它是否“觉得规则合理”不参与定稿。

## 七、以后修改制度的正确流程

### 第一步：保留原始现场

发现模型跑偏后，不要先提醒、解释或要求重做。先保存能够取得的原始信息：

- 用户实际提示词；
- 会话加载的规则来源、提交和文件哈希；
- 模型可见的项目入口和污染文件；
- 可取得的原始对话、工具调用和错误信息；
- 最终磁盘产物和 Git 状态。

提醒后的上下文已经改变，只能用于观察修正能力，不能代替原始失败现场。

### 第二步：确认规则是否真正进入上下文

分别检查源稿、远端、缓存和新会话使用的版本。没有证据证明模型看到了目标规则时，不能评价规则正文。

本轮第一次按正确方法推进，就是在这一步发现 DeepSeek 根本没有加载参考材料治理规则，从而停止继续修改正文，转去修复触发和路由。

### 第三步：还原因果关系

找出模型实际依据的原文，并回答：

1. 它是否正确理解了这句话？
2. 还有没有其他规则与它共同作用？
3. 该判断怎样转化成工具操作？
4. 工具操作是否直接产生了当前磁盘结果？

不要用最终结果倒推模型必然这样想。

### 第四步：确定问题层级

- 没有命中场景：修触发和路由；
- 加载了旧版：修发布和缓存证据链；
- 规则有多种合理解释：由人确定意图后消除歧义；
- 正确执行却产生错误结果：由人修改制度决定；
- 规则正确但模型漏执行：检查强制程度、入口和验收；
- 示例诱导错误：修示例；
- 工具机制假设错误：先实测机制，再修改制度；
- 上下文证据不足：保留假设，不改正式规则。

### 第五步：由人拍板

AI 提供证据、根因、影响范围和可选写法。人决定制度意图、接受的取舍和采用哪种处理方式。

### 第六步：AI 做最小修改

只修改造成问题的层级和条款，同时检查关联规则、示例、入口和验收是否冲突。不得趁机补齐未经人确认的“可能遗漏”。

### 第七步：重新测试具体效果

使用不泄露答案的自然任务，验证本次修改是否改变了目标行为。通过只表示当前问题在当前测试中没有再次出现，不构成制度完整性证明。

Herdr 调度、提示词保护、版本核验和产物审计的操作流程见项目级 [Herdr Pi 治理回归 skill](../.agents/skills/herdr-pi-governance-test/SKILL.md)。

## 八、本轮其他有效经验

### 1. 拆文件不等于完成场景升级

从开发规范拆出新文件时，必须重新定义治理对象和排除项。旧内容只能提供问题线索，不能直接当成新规范模板。

### 2. 不要用规则替模型完成常识判断

需要结合项目语境、存在多种合理答案的内容，只规定边界和必要结果；错误代价高、操作顺序唯一时，才使用强步骤。

### 3. 人类入口和 Agent 入口分开

README 服务人类判断和查找，AGENTS 保存人已经确定的长期维护契约，CLAUDE 只负责固定路由。入口之间链接，不复制正文。

### 4. 废弃不等于抹除来源

本地实体、当前采用状态和历史来源是三个不同对象。承担证据和追溯职责的信息，不能随本地存档一起删除。

### 5. 控制上下文占用

没有独立用途时，不同时长期保存 HTML、Markdown 等完整正文副本；长期入口不写动态数量、一次性命令和单项详情。

### 6. 当前状态不能替代条件规则

项目现在没有 Git，不代表以后不需要版本控制边界。长期入口保存条件成立时如何行动，不把当前状态写成永久结论。

### 7. 示例会影响模型行为

示例中的目录、名称、顺序和注释都可能被逐字执行。示例只能表达已经由人确定的质量下限，不能替人决定制度。

### 8. 外部机制必须实测

涉及 Git、缓存、权限、网络和工具加载机制时，先验证真实行为。不能用额外目录和复杂流程弥补对底层机制的误解。

### 9. 测试题不能泄露答案

真实测试只提供正常项目目标和必要来源，不写“治理测试”“按规范整理”“放入 reference”等提示。过于明显的题目只能测试模型能否照题作答。

### 10. 产物证据和原因证据缺一不可

磁盘扫描证明发生了什么，会话上下文说明为什么发生。只看回复会漏掉产物问题，只看产物又容易猜错根因。

### 11. 自动化成功要看业务结果

一次 Herdr 派发因 PowerShell 与 Bash 引号拼接导致提示词为空，但外层命令仍然返回成功。派发必须以目标 Agent 的 `agent_prompted` 事件为证据，不能只看退出码。

### 12. 先达到人的目标，再压缩文字

规则尚未产生预期行为时，过早压缩可能删掉仍需验证的内容。目标达成后再按信息价值合并重复表达，不以行数作为质量指标。

### 13. 长模板的强制约束必须贴近具体内容

对长模板而言，统一写在模板前后的一条强制要求，不如紧贴具体章节的局部约束有效。模型处理长模板时可能记住总体目标，却在生成后半段时漏掉末尾章节。

0.2.4 回归中，DeepSeek 已经读取完整规范，模板前也明确写了“必须逐章保留”。它最终仍只生成 8 个内部章节，漏掉最后的“维护结果验收”。结束前自查时，它没有重新读取源模板，而是凭记忆把预期章节列成 8 个，再用 `grep` 检查自己生成的文件，最终错误地声称“全部 8 章保留”。

由此确定两条做法：

- 必须保留的章节、步骤或边界，在对应内容附近直接标明，不能只靠长模板前后的统一重申；
- 验收模板产物时，同时重新读取规则源稿和最终产物逐项对照，不得凭记忆生成验收清单，也不得只检查最终产物。

## 九、后续拆分必须遵守的原则

### 原则 1：制度所有权属于人

人确定目标、边界、取舍、例外和定稿。AI 没有根据项目表现自行建立长期规则的权限。

### 原则 2：没有上下文证据，不修改制度

异常产物只能触发调查。无法证明模型加载了什么、依据了什么以及怎样产生结果时，只报告假设。

### 原则 3：先建立因果链，再讨论措辞

每次修改都要能指出具体规则、模型判断、操作和产物之间的关系。润色不能代替根因分析。

### 原则 4：AI 只在人的决定内优化

AI 可以提供选项、发现冲突和优化表达，但不能暗中替人扩大制度目标或增加新的治理职责。

### 原则 5：测试只能证伪和验证具体修改

一次失败可以暴露问题，一次通过不能证明制度完整。不同模型和新会话提供更多样本，不提供制度决策权。

### 原则 6：先定对象和边界

先回答“管什么、为什么管、什么不归它管”，再写目录、命名和流程。

### 原则 7：上层只路由，场景独立闭合

上层总纲只保留触发条件和规范链接。场景规范独立覆盖边界、入口、生命周期、危险操作和验收证据。

### 原则 8：项目 AGENTS 是人控制的维护契约

它只保存上层制度要求、可核验的稳定事实和人明确拍板的项目约束。AI 可以按契约落地，不能自由归纳并自行定稿。

### 原则 9：长期规则与当前状态分开

条件规则、稳定入口和长期边界进入 AGENTS；动态数量、当前版本、本次命令和临时选择进入相应事实文件或任务记录。

### 原则 10：示例只表达已确定的能力下限

示例不是制度决策来源。弱模型照搬也必须安全，强模型可以改善表达，但不能删除人已经确定的能力。

### 原则 11：上下文预算属于质量要求

每段长期内容至少帮助判断、定位、核验或维护。对人和 AI 都没有长期用途的内容不保留。

### 原则 12：外部机制先实测

规则涉及工具行为时，先取得实际证据。错误的机制假设不能写成强制制度。

### 原则 13：一条问题只在正确层修一次

路由、正文、示例、分发、上下文和工具机制分别处理，避免同一问题在多份文件重复加提示。

### 原则 14：修改采用最小范围

人确认方向后，只修根因和必要关联项。不得因一次失败顺便扩建尚未出现真实问题的规则。

### 原则 15：定稿权不能外包给模型

模型测试、磁盘验收和上下文分析为人提供证据；最终是否达到制度目标，由人判断。

## 十、场景规范的建立与定稿

### 建立新场景时

1. 人说明已经出现的真实问题和不接受的结果；
2. 人确定治理目标、对象、排除项和职责边界；
3. AI 查找现有规则、项目事实和可能冲突；
4. AI 根据人的决定起草或润色，不自行增加制度目标；
5. 人审阅并拍板条款；
6. AI 完成链接、表达、重复、上下文占用和一致性检查；
7. 使用自然任务观察实际行为；
8. 出现异常时按“原始上下文—因果链—人拍板”处理。

### 规范至少要回答

1. 这份制度要解决什么问题？
2. 哪些对象归它管理，哪些不归？
3. 人类、Agent 和工具分别从哪里进入？
4. 哪些内容是长期规则，哪些只是当前状态？
5. 生命周期如何变化？
6. 哪些动作可能丢失证据、污染其他项目或造成不可逆结果？
7. 项目 AGENTS 必须具备哪些由人确定的维护能力？
8. 用什么磁盘事实证明规则已经执行？
9. 出现偏差时到哪里取得原始上下文？
10. 哪些判断必须交还人类？

### 进入冻结观察期的条件

1. 人已经确认治理目标、职责边界和具体取舍；
2. 已知失败都有上下文和产物证据支持的根因结论；
3. 规则、示例、入口和验收之间没有已知矛盾；
4. 具体修改在自然任务中产生了人确认的预期行为；
5. 最终磁盘产物符合人的要求；
6. 源稿、远端、缓存和被测会话版本一致；
7. 没有未经人确认、仅凭 AI 猜测加入的条款；
8. 后续修改只由新的真实证据和人的决定触发。

“定稿”表示人基于当前证据确认制度可以使用，不表示模型已经证明制度完整，也不表示未来项目不再需要人的治理。
