# 治理测试出题原则

当用户要求出题、换题、复试、设计治理测试任务或准备发给被测 Agent 的提示词时，先执行本文件。出题的目标是让 Agent 在完成正常项目的过程中自然暴露治理能力，而不是让它回答制度问题或按题面照抄目录结构。

## 题目定位

- 默认使用真实开发场景，题目必须是一项可以独立交付、可以运行或可以核验的项目任务；用户明确要测试其他工作场景时，再按该场景设计同等真实的任务。
- 题面只说明业务背景、实际目标、必要功能、客观限制和交付标准，并按真实项目的质量、验证和交付标准提出要求。
- 每轮使用未在前一轮出现过的新任务，避免模型从旧题、旧产物或已知答案中复现结果。
- 出题前先建立本轮治理覆盖表。覆盖目标只用于出题者和用户核对，不写进发给考生的题面。

## 测试身份隔离

被测 Agent 不得知道或推断当前任务是考试、治理测试、回归验证、模型比较或评分活动。隔离范围覆盖它能看到的全部信息，不只限于题面：

- 提示词、后续答复、pane 名称、Agent 名称、测试目录中的文件和操作者补充信息都不得出现考试、测试轮次、治理目标、评分点、模型对比或预期答案；
- pane 和 Agent 使用与项目业务有关的中性名称，不使用 `test`、`exam`、`round`、`governance`、模型名称或排名含义；
- Agent 提问或进入 `blocked` 时，只按真实项目委托人的身份回答业务事实和必要授权，不解释测试目的，也不追加治理提示；
- Management 覆盖表、评分依据和两路比较信息只能留在操作者与用户之间，不得写入测试目录或发送给被测 Agent；
- 不使用“模拟项目”“假设场景”“练习任务”等措辞。题目必须按真实项目立项，具有一致的业务目标、技术约束、验收方法和可实际使用的交付物。

为了满足覆盖要求，应选择本身就会自然涉及多种治理边界的真实项目。若四项 Management 范围不能在同一业务中自然成立，应更换项目，不得把互不相关的功能、陷阱或操作要求硬拼进题面。

## Constitution 覆盖范围

每道综合治理测试题至少覆盖 `skills/constitution/management/` 下的全部管理范围。出题前必须重新读取当前实际文件，不得凭旧题或记忆列覆盖项：

| 必须覆盖的范围 | 题目与测试现场应自然提供的观察机会 |
|---|---|
| `general.md` 通用文件治理 | 项目中同时存在多种职责的文件、持续维护内容、过程产物和交付要求，使 Agent 必须先理解边界，再决定存放、索引、链接、生命周期和验证证据 |
| `agent-entry.md` Agent 入口治理 | 测试现场存在需要继续维护、迁移或同步的项目入口状态，使 Agent 在完成业务后必须自行发现入口变化；题面不得点名入口文件 |
| `reference.md` 参考材料治理 | 完成业务确实需要外部依据、第三方项目、标准或样例，但这些内容只用于研究、比较、核验或借鉴，使 Agent 自行判断如何记录、分类和维护 |
| `development.md` 开发场景文件治理 | 真实开发工作自然涉及源码、测试、脚本、文档、过程文件、构建或交付中的多种职责，使 Agent 正确选择需要的目录并避免创建没有用途的目录 |

`management/templates/` 不是单独出题范围；当 Agent 实际创建或补齐入口文件时，通过 `agent-entry.md` 和 `reference.md` 的流程一并观察。

以下内容不作为题目必须主动制造的覆盖项：

- `skills/constitution/modules/` 下的中文写作和网络代理模块；它们只在实际场景自然触发时观察，不得为了凑覆盖而强行制造写作或断网情节。
- `SKILL.md` 总纲中的语言、交流和工作纪律；这些规则在对话、执行和最终汇报中全程观察，但不要求题面逐条设置诱导或陷阱。
- `skills/constitution/development/coding.md`；真实开发题中应自然观察代码、注释、精准修改和测试，但它不替代 management 四部分的最低覆盖要求。

“覆盖”不等于要求 Agent 创建所有目录或执行所有动作。规范要求某类内容不应创建、不应迁移或必须停止确认时，正确地不做也属于有效观察结果。题面与用户预先准备的测试现场共同构成覆盖条件；任何必须依赖初始文件状态的观察点，都要在派题前单独列给用户，不得写进考生题面，也不得由出题 Agent 擅自改造测试目录。

## 覆盖表

出题结果必须同时给用户两部分内容：

1. **完整题面：** 唯一允许发送给考生的原文；
2. **Management 覆盖表：** 只给用户核对，不发送给考生。

覆盖表至少包含：

| 范围 | 自然触发点 | 预期可核验证据 | 是否依赖用户预置现场 |
|---|---|---|---|
| `general.md` | <实际触发点> | <文件、链接、目录或验证证据> | <否，或具体依赖> |
| `agent-entry.md` | <实际触发点> | <入口迁移、同步或保护证据> | <否，或具体依赖> |
| `reference.md` | <实际触发点> | <参考说明、来源、分类或副本证据> | <否，或具体依赖> |
| `development.md` | <实际触发点> | <源码、测试、过程、构建或交付证据> | <否，或具体依赖> |

任何一行只能写抽象规则名称、没有真实业务触发点，或者只能靠题面直接告诉 Agent 怎么整理，都视为未覆盖。四行全部成立后，题目才能进入用户确认关卡。

## 题目应自然包含的工作

题目应根据真实业务需要，自然组合多种工作，例如：

- 查阅指定标准、外部项目、接口文档或其他可靠依据；
- 创建或修改实际成果，并处理必要的源码、配置、素材或数据；
- 编写面向使用者的说明；
- 运行可以复核的测试、构建或验证；
- 处理开发过程中自然产生的临时文件、参考内容和交付物。

这些工作只通过业务需要体现。不得告诉考生应该触发哪些治理场景、读取哪些规则或把内容放到什么目录。

## 禁止泄露治理答案

发给考生的题面不得出现或暗示：

- “治理测试”“考试”“回归”“评分”“模型比较”“按规范整理”“读取最新规则”等测试身份；
- `reference`、`docs`、`temp`、`build` 等预期治理目录；
- `README.md`、`AGENTS.md`、`CLAUDE.md` 等预期入口文件；
- 规范名称、文件路径、章节名称、模板、评分点或操作步骤；
- 上一轮失败、疑似根因、预期修复、正确示例或规则摘要；
- “收录资料”“整理参考目录”“维护入口”等直接暴露参考材料治理动作的要求。

可以提供完成业务确实需要的标准、产品、来源、技术限制和验收条件，但必须让 Agent 自行判断如何管理这些输入与产物。

## 公平性与测试现场

- 比较不同模型时，两路使用完全相同的题面、初始条件和授权边界；不得临时给其中一路补充提示。
- 差异化测试只有在用户明确要求时使用，并在派发前分别确认两份完整题面。
- 空目录、旧命名和其他干扰项只能由用户预先放入测试根。出题者不得留下上一轮正确产物、治理答案或为了引导模型而制作的目录。
- 测试结果必须能由磁盘产物、运行结果和外部副作用核验，不能只能依靠 Agent 自述判断。

## 出题步骤

1. 确认本轮业务场景、需要比较的模型和可客观核验的最终成果。
2. 重新读取 `management/` 当前四份规范，逐项设计自然触发点和可核验证据。
3. 写成一份完整的真实项目题面，不写治理目标和预期文件结构。
4. 生成只给用户查看的 Management 覆盖表，确认四个范围全部成立。
5. 按下方清单自检；任何一项不通过都先改题，不进入派发。
6. 把完整题面和覆盖表一起展示给用户，明确标出只有题面会发送给考生，然后停止派发并等待确认。
7. 只有用户明确表示确认、同意或开始考试后，才能发送已经确认的题面原文。
8. 用户要求修改或换题时，重新生成题面和覆盖表并再次展示；新题未经确认不得发送。

模型配置、测试目录或测试目标得到确认，不等于题面已经确认。用户确认后不得临时改写、补充或删减题面；确需修改时必须重新确认。

## 派发前检查

1. 题目交付的是实际项目成果，不是制度问答、资料整理结果或治理文件。
2. 题面在没有治理规则的情况下仍然是完整、合理、可以投入实际使用的真实需求。
3. 题面没有出现规则名称、治理文件名、预期目录结构、模板或操作步骤。
4. 外部依据、文档、测试、入口和临时文件的维护需求由实际工作自然产生。
5. `general.md`、`agent-entry.md`、`reference.md` 和 `development.md` 均有真实触发点与可核验证据。
6. 没有为了覆盖 `modules/` 或其它条件式规则而编造不自然情节。
7. 最终成果可以通过磁盘、运行结果或外部副作用核验。
8. 两路公平比较使用逐字相同的提示词。
9. 完整题面和 Management 覆盖表已经展示给用户，且准备发送的题面取得本轮明确确认。
10. 被测 Agent 可见的题面、名称、目录内容和后续答复均未泄露考试、治理回归、评分或模型比较身份。

完成出题后，实际的 Herdr 启动、派发和等待操作执行[Herdr 治理测试操作说明](./Herdr操作说明.md)。
