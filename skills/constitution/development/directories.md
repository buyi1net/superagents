# 目录规范

## 规则范围

- 本规范只管理项目目录，不管理代码标识符、配置键或技术栈内部约定。
- 根目录只允许登记的九个项目目录：`archive/`、`design/`、`build/`、`docs/`、`reference/`、`scripts/`、`source/`、`temp/`、`tests/`。
- 一级目录按需创建，不预建空目录。不得自行新增未登记的一级目录；确需新增时，先取得用户明确批准并更新 `AGENTS.md`。
- `.agents/`、`.claude/`、`.pi/` 等是 Agent 工具目录，为 Agent工具自动创建，不得改作项目分类。

## 活动边界

- 项目根目录是 Agent 默认的读取、搜索、执行和写入边界。除用户明确指定的外部位置外，不得读取、枚举、搜索、比较、复制、移动、修改或创建项目根目录之外的文件和目录。
- 不得查看父目录、兄弟项目、其他 Agent 工作区或它们的任务记录，也不得从中复制实现。指向项目根目录之外的符号链接、快捷方式和挂载路径同样属于边界外内容。
- 可以调用系统已安装的解释器、编译器和开发工具，但项目源码、日志、缓存、中间文件和交付物必须写入本项目允许的位置。任务确实依赖未明确提供的外部文件时，先报告所需路径和用途，取得用户明确许可后再访问。

## 命名规则

- 工程目录使用小写英文；多词使用短横线 `-`；禁用空格、下划线和驼峰。
- 直接面向人类阅读的制度、交付等文档目录可使用简体中文。
- 一级目录下的二级目录和子项目，默认继承所属一级目录的语言、大小写和分隔符偏好。
- `source/`、`scripts/` 等工程目录使用英文；`docs/` 等面向人类阅读的目录可使用简体中文。
- 同一层级的目录必须保持命名风格一致；已有目录可以容纳的内容，不得再创建名称不同但用途相同的目录。
- 一级目录的 `README.md` 可以补充本目录及其子目录的命名规则，但只能比本规范更具体，不能与本规范冲突，也不能影响其他一级目录。
- 技术栈或工具链强制要求的目录名称可以例外，例如 `src/`、`cmd/`、`internal/`；例外只为满足工具要求，不得借此新增项目分类。
- 一级目录下的子目录，按实际内容和所用技术栈创建；没有明确用途的目录不得提前创建。
- 所有用于导航、说明、索引或清单的文件中，指向项目内文件或目录的引用，都必须使用相对路径，不得使用本机绝对路径。文件格式支持超链接时，必须使用该格式的原生可点击链接语法；不支持超链接的纯文本格式，至少写出项目根内的相对路径。不得把规则限定为某一种文件格式。代码导入、模块引用和工具链内部路径不属于本条。外部资源必须使用完整 URL；格式支持超链接时，应使用其原生链接语法。

### 归类优先

- 新增、移动或恢复任何内容前，先根据其长期用途判断所属分类，再决定落点；不得因为当前只有一个文件或目录就跳过归类。
- 各一级目录的根部只保留局部入口和分类目录；内容不得直接散放在根部。已有分类可以容纳时，不得另建同义分类。
- 没有合适分类时，先创建一个用途明确、可长期复用的分类目录并更新地图；不得用“临时”“杂项”“其他”等模糊目录掩盖尚未完成的归类。
- 无法判断归属时先暂停写入并报告，不得把内容随意放入 `temp/` 或任意现有目录。
- 分类按预期用途治理，不按当前文件数量治理；目录即使暂时只有一项内容，也应放在未来可延续的分类中。

## 一级目录职责

### `archive/`：历史归档

存放已经退出当前开发流程、但仍需要保留的阶段版本、旧方案和废弃设计。

- 只在重要阶段或版本节点归档，不为每次小修改复制一份。
- 归档目录按 `名称-版本-备份时间` 命名，时间使用 `YYYYMMDD-HHmm` 格式，例如 `task-cli-v0.1.0-20260813-1430/`。
- 每个归档项应有自己的 `README.md` 或归档说明，记录归档日期、原因和替代版本；内部链接使用相对路径。
- `archive/` 根目录只放局部入口和归档项目目录，不直接散放归档文件。
- 归档内容默认只读，不参与当前构建、测试或运行，当前代码不得依赖它。

### `design/`：设计资料

存放开始实现前使用的原型、交互流程、视觉稿、设计系统和设计令牌。

- 新增页面、新功能或明显改变交互时，应先在本目录形成明确的设计方案，再开始编码；紧急修复除外。
- 设计根目录只放局部入口和设计项目目录，设计文件不得直接散落在根部。
- 每个独立设计项目必须有说明文件；可交互原型按项目单独组织，不得和其他原型混放。
- 设计项目内按需要使用 `prototype/`（可交互原型）、`assets/`（设计资产）、`docs/`（详细说明）、`exports/`（导出预览）等子目录；只在实际需要时创建。
- 设计软件源文件、原型文件、视觉稿和预览图放在对应的设计项目内；项目背景、设计决策和交付说明放在 `docs/`。

### `build/`：项目级构建与交付物

存放多个子项目构建后汇总的最终产物、安装包、发布包、部署包和校验文件。

- `build/` 是面向人工检查和交付的统一出口，不是所有工具的中间构建目录。
- `build/` 根目录只放局部入口和项目或子项目产物目录，不直接散放压缩包、报告或校验文件。
- 每个产物目录按需要分为 `release/`（发布产物）、`checksums/`（校验文件）、`metadata/`（构建清单和报告）；不需要的类别不建。
- 子项目可按技术栈保留中间产物，但应配置到临时位置或纳入忽略规则。
- 目录内容必须可以重新生成，不得作为唯一源文件或运行时依赖。

### `docs/`：项目文档

存放长期维护、面向人类阅读的项目文档，包括研发治理、交付管理、使用说明和决策记录。

- 文档按受众和用途建立二级目录，避免按个人姓名、临时任务或文件格式分类。
- `docs/` 根目录只放局部入口和文档领域目录，不直接散放业务文档。文档领域按研发治理、交付管理、产品文档、技术文档、用户文档等用途分流，只创建实际需要的领域。
- 文档领域可按主题或产品建立更深层目录；同一类文档不得散落在多个领域。
- `docs/` 不存放设计源文件、参考项目副本、构建产物或临时日志。

### `reference/`：外部参考资料

存放与项目相关的参考项目、参考代码、第三方文档、样例和素材。

- 参考内容默认只读，不得直接作为当前项目的源码、运行依赖或构建输入。
- `reference/` 根目录只放 `README.md` 和参考分类目录，参考文件不直接散落在根部。分类按参考对象划分，至少区分 `projects/`（完整项目参考）和 `implementations/`（功能实现参考）；不按人类或 AI 的发现来源划分。
- `projects/` 用于存放完整项目、参考仓库或可整体借鉴的产品案例，关注架构、目录、交互、工程流程等整体经验；`implementations/` 用于存放某个功能、算法、组件、接口或技术方案的实现参考。两类内容不得混放。
- `reference/README.md` 必须包含“参考项目”和“功能实现参考”两个章节。每条至少写明名称、来源、写入日期、用途和路径；项目内路径用相对链接，外部资源写完整 URL。人类和 AI 都可以维护这两类清单，但维护者不是分类依据。
- 复制进来的外部资料应记录来源、版本、获取日期和许可信息；能用链接解决的，不重复保存整份副本。

### `scripts/`：可复用项目脚本

存放项目级、可重复执行的构建、测试、部署、迁移、校验和数据处理脚本。

- 根目录脚本应服务于整个项目；只属于某个子项目的脚本放入对应的 `source/` 子目录。
- `scripts/` 根目录只放局部入口和脚本分类目录，不直接散放脚本。脚本按构建、测试、发布、迁移、校验、维护等用途分流，只创建实际需要的分类。
- 一次性排查、转换或实验脚本放入 `temp/`，不得让 `scripts/` 变成临时文件仓库。
- 脚本应说明用途、输入、输出和执行前提；涉及删除、覆盖或外部写入时必须明确风险。

### `source/`：正式源代码

存放项目的业务源代码及其子项目。无论使用何种技术栈，项目自有的正式源代码只能位于本目录。

- 完整交付物由多个可独立构建、测试或部署的单元组成时，按“交付项目—独立子项目”组织：`source/<交付项目>/<子项目>/`。只有一个独立单元时，可直接使用 `source/<项目>/`。
- `source/` 根目录只放局部入口和交付项目目录，不直接散放源码文件；采用“交付项目—子项目”分组时，交付项目目录只放其独立子项目和必要的项目级配置；单项目可直接在项目目录内放置技术栈源码。
- 每个交付项目和每个独立子项目都必须有自己的 `README.md`，说明边界、用途、运行方式、测试方式和直接子目录。普通包、功能模块和技术栈内部目录不是项目单元，不单独创建入口。
- 仅服务于一个项目的功能模块、包和共享代码，留在该项目或子项目的技术栈目录内；跨多个项目复用、且需要独立版本或测试的代码，提升为 `source/` 下的独立项目单元。
- 子项目的源码、资源、技术栈配置和专属脚本可在其目录内组织；项目内部最多再向下展开技术栈所需目录，不得继续把每个功能拆成新的项目层级。
- 根目录仅保留项目级入口、治理文件和工具链要求必须位于根部的配置；不得把业务源码散落在根目录。

### `temp/`：可删除临时区

存放日志、截图、下载文件、中间文件、缓存、实验代码和 Agent 工作文件。

- `temp/` 中的内容必须可以随时删除，清空后不得造成项目实质损失。
- `temp/` 根目录只放局部入口和按任务或会话划分的临时子目录，不直接散放日志、截图和中间文件。临时子目录建议使用 `任务名-日期时间` 命名。
- “暂时不知道放哪里”不是使用本目录的理由；无法确认可删除性时，必须先完成归属判断。
- 临时内容不得被正式源码、文档、构建或部署流程依赖。

### `tests/`：项目级测试

存放跨子项目的集成测试、端到端测试、回归测试、验收测试和公共测试数据。

- 单元测试和技术栈要求与源码同目录的测试，放在对应的 `source/` 子项目内。
- `tests/` 不是必建目录；只有出现项目级测试需求时才创建。
- `tests/` 根目录只放局部入口和测试分类目录，不直接散放测试文件。可按集成、端到端、验收、回归、公共数据等用途分流，只创建实际需要的分类。
- 测试应能表达设计或需求中的可验证条件，不能只为增加数量而创建。

## 执行要求

- 涉及目录变更或无法判断归属时，先读本规范，再读目标目录的入口文件。入口默认为 `README.md`；同时存在 `AGENTS.md` 时，两者都要读。
- 目标是已设入口的二级目录或子项目时，必须读该入口；目标尚不存在时，读最近的上级入口。
- 新建一级目录时，必须在同一任务中创建它的局部入口。
- 目录变更完成后，重新扫描实际结构，并更新受影响目录的入口。删除目录时，必须同时清理上级入口中的过期记录。
- 发现地图与实际结构不一致时，先判断差异是否由本次任务造成。是本次任务造成的，应在收尾前更新受影响的入口。
- 是人类或其他 Agent 并行修改造成的，应保留对方改动并避免覆盖；无法判断时，先报告差异和影响，不得擅自重写地图。
- 未涉及目录变更的任务，无需读取本规范和目录入口。

## 局部入口与目录地图

- 每个已创建的项目级一级目录必须有 `README.md`；只有存在额外 Agent 约束时，才在同级增加 `AGENTS.md`。进入目录前，存在的入口文件都要读。
- 一级目录必须维护局部入口；普通二级目录按复杂度决定是否维护。独立子项目必须按所属职责提供入口；除本规范明确要求的独立子项目外，三级及更深技术目录不得继续创建 `README.md` 或 `AGENTS.md`，入口不得向下扩散。
- `README.md` 只说明本目录用途、命名补充、直接子目录地图和必要的使用方法，不得复制整棵文件树或重复总规范。
- 目录地图只记录直接子目录，每项只写“当前文件格式可导航的相对链接、用途”。没有直接子目录时写“暂无”，不要建立空表格；支持超链接的格式不得把路径写成普通文本或仅用代码格式包裹。
- 禁止在入口文件中建立任何文件清单，包括主要入口、当前文件、源码文件、测试文件和生成文件；不得逐个标记或说明文件。
- 新建、移动、重命名或删除目录后，必须重新扫描实际结构，并在同一任务内更新最近的上级入口。删除目录时，必须移除对应的过期记录。
- 地图只用于导航当前直接子目录，不是对整个文件树的备份；不得用地图覆盖人类或其他 Agent 的并行修改。
- 局部入口是导航和操作摘要，只保留目录用途、命名补充、直接子目录地图和必要使用方法。详细说明应放入该目录允许的 `docs/` 或现有文档，入口不得复制整个文件树。
- 不设置局部入口的固定行数上限；入口过长时，应删除重复内容、改用链接或下沉详细文档，但不得删除必要规则，也不得向三级及更深目录扩散入口文件。

## 规范保护

- 本文件由用户维护。除非用户明确要求，Agent 不得修改、移动、删除、压缩或放宽本文件。
- 发现规范与项目需求冲突时，先报告冲突和影响；不得用修改规范的方式绕过约束。
