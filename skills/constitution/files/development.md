# 文件治理：开发场景

本规范适用于代码项目的创建、开发、构建、测试和交付。使用本规范前，先读取 `files/general.md`；本文件只补充代码项目专用的文件结构和归类规则。

## 统一项目分类

- 代码项目的项目分类一级目录只允许以下九类：`archive/`、`design/`、`build/`、`docs/`、`reference/`、`scripts/`、`source/`、`temp/`、`tests/`。
- 一级目录按需创建，不预建空目录。不得自行新增未登记的一级目录；确需新增时，先取得用户明确批准，并在同一任务中更新受影响的项目地图。
- `.agents/`、`.claude/`、`.pi/`、`.git/` 等工具、版本控制或 Agent 运行目录不属于项目分类，不得改作项目分类，也不纳入人工维护的项目地图。
- 代码项目根目录只保留项目级入口、治理文件和工具链强制要求位于根部的配置文件；业务源码、测试文件、构建产物、日志和下载资料不得直接散放在根目录。

## 命名和层级

- 工程目录使用小写英文；多词使用短横线 `-`；禁用空格、下划线和驼峰。
- 直接面向人类阅读的制度、交付等文档目录可使用简体中文。
- 一级目录下的二级目录和子项目，默认继承所属一级目录的语言、大小写和分隔符偏好。
- `source/`、`scripts/` 等工程目录使用英文；`docs/` 等面向人类阅读的目录可使用简体中文。
- 同一层级的目录必须保持命名风格一致；已有目录可以容纳的内容，不得再创建名称不同但用途相同的目录。
- 技术栈或工具链强制要求的目录名称可以例外，例如 `src/`、`cmd/`、`internal/`；例外只为满足工具要求，不得借此新增项目分类。
- 一级目录下的子目录按实际内容和所用技术栈创建；没有明确用途的目录不得提前创建。

## 一级目录职责

### `archive/`：历史归档

存放已经退出当前开发流程、但仍需要保留的阶段版本、旧方案和废弃设计。

- 只在重要阶段或版本节点归档，不为每次小修改复制一份。
- 归档目录按 `名称-版本-备份时间` 命名，时间使用 `YYYYMMDD-HHmm` 格式，例如 `task-cli-v0.1.0-20260813-1430/`。
- 每个归档项应有自己的 `README.md` 或归档说明，记录归档日期、原因和替代版本；内部链接使用相对路径。
- `archive/` 根目录只放局部入口和归档项目目录，不直接散放归档文件。
- 归档内容默认只读，不参与当前构建、测试或运行，当前代码不得依赖它。

### `design/`：设计资料

存放原型、交互流程、视觉稿、设计系统和设计令牌。

- 需要设计资料的新增页面、新功能或明显改变交互，应在本目录形成对应设计项目；设计先行的具体流程由开发规范规定，紧急修复除外。
- 设计根目录只放局部入口和设计项目目录，设计文件不得直接散落在根部。
- 每个独立设计项目必须有说明文件；可交互原型按项目单独组织，不得和其他原型混放。
- 设计项目内按需要使用 `prototype/`、`assets/`、`docs/`、`exports/` 等子目录，只在实际需要时创建。
- 设计源文件、原型文件、视觉稿和预览图放在对应设计项目内；项目背景、设计决策和交付说明放入项目文档。

### `build/`：项目级构建与交付物

存放项目构建后的最终产物、安装包、发布包、部署包和校验文件。

- `build/` 是面向人工检查和交付的统一出口，不是所有工具的中间构建目录。
- `build/` 根目录只放局部入口和项目或子项目产物目录，不直接散放压缩包、报告或校验文件。
- 每个产物目录按需要分为 `release/`、`checksums/`、`metadata/`；不需要的类别不建。
- 子项目可按技术栈保留中间产物，但应配置到临时位置或纳入忽略规则。
- 目录内容必须可以重新生成，不得作为唯一源文件或运行时依赖。

### `docs/`：项目文档

存放长期维护、面向人类阅读的项目文档，包括研发治理、交付管理、使用说明和决策记录。

- 文档按受众和用途建立二级目录，避免按个人姓名、临时任务或文件格式分类。
- `docs/` 根目录只放局部入口和文档领域目录，不直接散放业务文档。
- 文档领域按研发治理、交付管理、产品文档、技术文档、用户文档等用途分流，只创建实际需要的领域。
- `docs/` 不存放设计源文件、参考项目副本、构建产物或临时日志。

### `reference/`：外部参考资料

存放与项目相关的参考项目、参考代码、第三方文档、样例和素材。

- 参考内容默认只读，不得直接作为当前项目的源码、运行依赖或构建输入。
- `reference/` 根目录只放 `README.md` 和参考分类目录，参考文件不直接散落在根部。
- 至少区分 `projects/`（完整项目参考）和 `implementations/`（功能实现参考）；两类内容不得混放。
- `projects/` 用于完整项目、参考仓库或可整体借鉴的产品案例；`implementations/` 用于功能、算法、组件、接口或技术方案参考。
- `reference/README.md` 必须包含“参考项目”和“功能实现参考”两个章节，并记录名称、来源、写入日期、用途和路径。
- 复制进来的外部资料应记录来源、版本、获取日期和许可信息；能用链接解决的，不重复保存整份副本。
- 从外部 URL、代码仓库或发布站点复制、克隆或下载的完整项目，默认归入 `reference/projects/`，不得因为它将被构建、运行或交付而直接归入 `source/`。
- `source/` 只存项目自有正式源代码。外部项目即使被修改或用于构建，也必须保留来源、版本、许可和改动范围记录，不得把完整上游副本冒充项目自有源代码。
- 任务实际保存外部完整项目副本时，必须同时维护 `reference/README.md` 和 `reference/projects/` 下的项目记录；只使用外部链接而不保存副本时，不得为了形式创建整份项目副本。

### `scripts/`：可复用项目脚本

存放项目级、可重复执行的构建、测试、部署、迁移、校验和数据处理脚本。

- 根目录脚本应服务于整个项目；只属于某个子项目的脚本放入对应的 `source/` 子目录。
- `scripts/` 根目录只放局部入口和脚本分类目录，不直接散放脚本。
- 一次性排查、转换或实验脚本放入 `temp/`，不得让 `scripts/` 变成临时文件仓库。
- 脚本应说明用途、输入、输出和执行前提；涉及删除、覆盖或外部写入时必须明确风险。

### `source/`：正式源代码

存放项目的业务源代码及其子项目。项目自有的正式源代码只能位于本目录。

- 完整交付物由多个可独立构建、测试或部署的单元组成时，按 `source/<交付项目>/<子项目>/` 组织；只有一个独立单元时，可直接使用 `source/<项目>/`。
- `source/` 根目录只放局部入口和交付项目目录，不直接散放源码文件。
- 每个交付项目和每个独立子项目都必须有自己的 `README.md`，说明边界、用途、运行方式、测试方式和直接子目录。
- 仅服务于一个项目的功能模块、包和共享代码，留在该项目或子项目的技术栈目录内；跨多个项目复用且需要独立版本或测试的代码，才提升为 `source/` 下的独立项目单元。
- 子项目的源码、资源、技术栈配置和专属脚本可在其目录内组织；不得继续把每个功能拆成新的项目层级。
- `target/`、`node_modules/`、`out/`、`dist/` 等工具链生成目录不是项目分类目录，不要求单独创建 `README.md` 或在人工地图中逐项展开，但必须纳入忽略规则或明确标记为可重新生成。

### `temp/`：可删除临时区

存放日志、截图、下载文件、中间文件、缓存、实验代码和 Agent 工作文件。

- `temp/` 中的内容必须可以随时删除，清空后不得造成项目实质损失。
- `temp/` 根目录只放局部入口和按任务或会话划分的临时子目录，不直接散放日志、截图和中间文件。
- “暂时不知道放哪里”不是使用本目录的理由；无法确认可删除性时，必须先完成归属判断。
- 临时内容不得被正式源码、文档、构建或部署流程依赖。

### `tests/`：项目级测试

存放跨子项目的集成测试、端到端测试、回归测试、验收测试和公共测试数据。

- 单元测试和技术栈要求与源码同目录的测试，放在对应的 `source/` 子项目内。
- `tests/` 不是必建目录；只有出现项目级测试需求时才创建。
- `tests/` 根目录只放局部入口和测试分类目录，不直接散放测试文件。
- 测试应能表达设计或需求中的可验证条件，不能只为增加数量而创建。

## 既有项目兼容

- 老项目接入本规范时，不得自动搬迁、重命名或删除既有目录。
- 进入老项目后，先扫描实际结构，记录与本规范的差异、原因和影响。
- 新增内容必须按本规范归类，不得因为旧项目存在不规范目录就继续扩展该目录。
- 工具链强制要求的目录可以保留，但必须说明其技术原因；它们不因此成为新的项目分类。
- 目录迁移只有在用户明确要求，或当前任务确实必须迁移时才能进行。
- 项目地图应反映实际结构，并单独记录仍保留的历史例外。

## 开发项目入口与地图

- 涉及代码项目的文件或目录变更时，先读取本文件和 `files/general.md`，再读取目标目录的入口文件。
- 入口默认为 `README.md`；同时存在 `AGENTS.md` 时，读取其路由并按指向继续读取相关规则。
- 新建一级目录时，必须在同一任务中创建它的局部入口，并更新受影响的项目地图。
- 每个已创建的项目级一级目录必须有 `README.md`；只有需要局部路由时，才在同级增加 `AGENTS.md`。
- `AGENTS.md` 只负责路由，不作为项目目录地图、动态状态表或交付日志；局部规则正文应放入被路由到的规范文件。
- `README.md` 只说明本目录用途、命名补充、直接子目录地图和必要的使用方法，不得复制整棵文件树或重复总规范。
- 目录地图只记录当前实际存在的直接子目录，不是整个文件树的备份；不得把制度允许但尚未创建的目录写成当前结构。
- 新建、移动、重命名或删除目录后，必须重新扫描实际结构，并在同一任务内更新最近的上级入口。
- 发现地图与实际结构不一致时，先判断差异是否由本次任务造成；无法判断时保留对方改动并报告差异和影响。

## 开发场景下的规范保护

- 本文件由用户维护。除非用户明确要求，Agent 不得修改、移动、删除、压缩或放宽本文件。
- 发现本文件与项目需求或既有结构冲突时，先报告冲突和影响，不得用修改本文件的方式绕过约束。
