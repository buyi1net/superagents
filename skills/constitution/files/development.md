# 文件治理：开发场景

本文件适用于代码项目的创建、开发、构建、测试和交付，必须与 [general.md](general.md) 一起读取。它只补充开发项目的一级目录职责，以及源码、测试、设计、文档、构建和交付的专用边界。

## 一、开发场景的目标

开发项目的结构要让接手者找到源码、运行和测试方式、可删除后重建的内容，以及交付物的取得位置。项目大小决定地图深度和分类数量；简单项目优先少层级，复杂项目再按职责和生命周期细分。

## 二、项目初始化

新建代码项目或首次接入既有项目时，顺序固定为：

1. 检查根目录和已有入口，先读取 [general.md](general.md)、本文件以及目标目录中已有的入口文件。
2. 按通用入口规则确认或补齐根目录 `README.md`、`AGENTS.md` 和 `CLAUDE.md`。
3. 在 `README.md` 建立当前实际的直接目录地图，在 `AGENTS.md` 建立规则路由；只创建实际需要的一级目录和维护子目录。
4. 明确项目是开发项目、构建暂存根、交付包还是运行实例，不让同一目录同时承担互相冲突的生命周期。
5. 开发、测试、构建和交付结束后，执行通用治理验收以及本文件的目录专用检查，再报告完成。

## 三、九类一级目录的默认分工

新增一级目录默认仅使用以下九类；是否创建由实际任务内容决定。

| 目录 | 放什么 | 不放什么 |
| --- | --- | --- |
| `archive/` | 已退出当前流程但仍需保留的旧版本、旧方案和阶段成果 | 当前构建依赖、临时备份 |
| `design/` | 视觉设计、交互流程、页面原型、设计系统和设计验证材料 | 架构文档、技术文档、业务源码、运行数据、构建包 |
| `build/` | 构建暂存目录、可运行包、源码交接包、校验和及构建元数据 | 运行数据库、日志、缓存、唯一源文件 |
| `docs/` | 项目全部长期维护的使用、技术、架构、决策、计划和交付文档 | 视觉设计源文件、业务源码、参考项目副本、临时报告 |
| `reference/` | 外部项目、第三方文档、功能实现参考和样例素材 | 项目自有源码、默认运行依赖 |
| `scripts/` | 可重复执行的构建、测试、部署、迁移、校验和数据处理脚本 | 业务源码、正式测试、一次性实验脚本 |
| `source/` | 项目自有正式源码和独立交付单元 | 完整外部上游项目、运行数据、临时文件 |
| `temp/` | 可随时删除的日志、截图、缓存、实验文件和 Agent 工作文件 | 正式源码、正式测试、构建唯一输入 |
| `tests/` | 跨子项目、集成、端到端、回归、验收测试和公共测试数据 | 只属于一个模块的单元测试 |

既有项目可以保留工具链强制目录和历史例外，但新增内容默认不得继续扩大已有的不合理归属；迁移、删除或重命名必须有用户授权或任务必要性。

一级目录的通用分类、说明文件、运行数据、生成物、临时物、交付类型和证据规则以 [general.md](general.md) 为准；以下内容只补充开发目录的专用边界。

## 四、各目录的专用规则

### `archive/`

作用：保存已退出当前开发流程、但仍需长期保留的旧版本、旧方案和阶段成果。归档内容默认只读，不参与当前源码、构建、测试或运行。

边界：

- 包含多个文件的归档项必须打包为 `.zip`；只有一个文件的归档项可以保留原格式。
- 归档包或归档文件使用 `名称-版本-YYYYMMDD-HHmm` 命名；压缩归档的完整名称以 `.zip` 结尾。
- `archive/README.md` 是归档索引，记录当前实际存在的归档项、版本、时间和用途；不记录实时工作日志。
- 当前仍在开发、构建、测试或运行所需的内容、临时备份、实时日志和未完成材料不得放入 `archive/`，当前流程也不得依赖归档内容。

### `design/`

作用：只存放视觉和交互设计资料，以及用于验证这些设计的原型资料。图片、设计文档和原型代码按设计意图归类，不按文件格式拆散。

边界：

- 可以包含视觉稿、页面原型、交互流程、设计系统、设计令牌、研究记录和交互验证用原型代码。
- 同一设计意图的相关材料应放在同一设计目录；存在两个或以上独立设计意图时，建立二级分类目录，例如 `visual/`、`prototype/`、`research/`。
- 架构、数据模型、技术选型、实施计划、用户手册和交付说明属于 `docs/`，不属于 `design/`。
- 正式业务源码放入 `source/`；运行截图和临时导出物放入 `temp/<任务或会话>/`。

### `build/`

作用：保存构建流程生成的构建暂存物、交付目录、发布包、安装包、部署包、校验和及构建元数据。它不是开发项目根，也不是运行实例根。

边界：

- 简单单项目可以使用 `build/<项目>-<版本>/`；只有存在多个交付类型、发布渠道或阶段时，才增加 `release/`、`checksums/`、`metadata/` 等层级。
- 构建前必须声明交付类型。可运行包与完整源码交接包的内容边界不同，必须在交付说明中写明使用者和包含范围。
- 交付目录和 ZIP 同时存在时，二者必须来自同一份文件清单；如果交付目录只是暂存，应明确标注并可在打包后删除。
- 构建目录不得直接运行。运行验证必须在解压副本或临时副本执行，验证后复查构建目录、交付目录和 ZIP。
- `__pycache__`、运行数据库、日志、截图、缓存、锁、进程文件和上传文件不得进入构建暂存根或初始交付包。
- 交付包 README 只有在接口需要时保留；它只说明如何取得、运行、验证或集成交付物，不复制开发项目根 README。

### `docs/`

作用：存放整个项目的长期维护文档，面向人类和接手项目的 Agent。

边界：

- 可以包含用户说明、技术说明、架构说明、数据格式、实施计划、决策记录、构建说明、交付说明和运维说明。
- `docs/` 根部原则上只放 `README.md` 和实际存在的文档主题目录，例如 `usage/`、`technical/`、`architecture/`、`decisions/`、`delivery/`。
- 存在两个或以上独立文档主题时，必须建立二级分类目录；只有一个主题且规模很小时，才可以直接放在根部，并在 `docs/README.md` 说明理由。
- 视觉设计源文件和交互原型放入 `design/`；临时报告和实时日志放入 `temp/<任务或会话>/`。

### `reference/`

作用：保存项目以外的参考资料，包括完整外部项目、第三方文档、标准、算法、组件、接口参考和样例素材。

边界：

- 根部只放 `README.md` 和实际存在的参考分类；存在多个参考类型时，按用途建立二级目录，例如 `projects/`、`standards/`、`implementations/`、`examples/`。
- 不为不存在的参考类型创建空目录；只有一种参考类型且规模很小时，可以直接放在根部，并在 README 中说明理由。
- 完整外部项目默认放 `reference/projects/`，不得因需运行、构建或修改而放入 `source/`。
- 保存外部资料时记录来源、版本、获取日期、许可证、用途和相对路径；能用 URL 解决的，不重复保存整份副本。
- 不得让运行时默认依赖指向未经说明的参考副本，也不得保存来源或许可证不明的材料。

### `scripts/`

作用：存放可重复执行的自动化脚本。

边界：

- 脚本按操作用途归类，例如 `runtime/`、`test/`、`build/`、`data/`、`deploy/`；存在两个或以上独立用途时必须建立二级分类目录。
- 根部只保留 `README.md`、必要的 `AGENTS.md` 和实际存在的用途分类目录；只有一个脚本且没有分类价值时，才可以直接放在根部，并在 README 中说明理由和运行方式。
- 可重复脚本必须说明输入、输出、副作用和前置条件；一次性实验脚本放入 `temp/<任务或会话>/`。
- 不得把业务源码、正式测试或不可重复的一次性实验长期放在 `scripts/`，也不得隐藏未声明的外部写入、安装、删除或数据修改行为。

### `source/`

作用：存放项目自有的正式源码、可维护技术包和独立交付单元，是项目实现的唯一权威来源；`source/README.md` 是源码区总览。

边界：

- 项目自有正式源码只能位于 `source/` 下；一个独立交付单元通常使用 `source/<项目>/`，多个可独立构建或部署的单元可使用 `source/<类别>/<项目>/`。
- `source/README.md` 必须说明源码区边界、实际直接子项目、每个子项目的主要职责、主要入口、运行和测试方式，以及子项目之间的关系。
- `source/README.md` 只描述直接子项目、公开入口和职责边界，不逐个解释实现文件、函数和类，也不维护完整文件清单。
- 直接子项目、重要技术包或大型拆分单元是否增加 README，按独立职责、运行边界和规模判断；需要时由子项目 README 说明自身入口、运行和测试方式。
- `target/`、`node_modules/`、`out/`、`dist/` 等工具链生成目录不属于源码分类，不要求逐层人工说明，但必须可重建并纳入忽略规则或上级说明。
- 不得把完整外部上游项目、参考副本、运行数据或临时文件放入 `source/`，也不得让多个项目共用无边界的源码目录。

### `tests/`

作用：存放跨模块或跨项目的集成、端到端、回归、验收测试和公共测试数据；单模块单元测试保留在对应源码项目内。

边界：

- 项目级 `tests/` 按测试性质分为实际存在的分类，例如 `integration/`、`e2e/`、`regression/` 或 `acceptance/`；只有一个类别且规模很小时，才可以在根部直接放测试文件，并在 README 中说明理由。
- 只验证单个模块且不启动真实服务的单元测试，放在对应 `source/<项目>/tests/`；启动真实服务、访问真实 HTTP/API、跨模块验证完整流程或面向交付验收的测试，放项目级 `tests/`。
- 面向用户验收的集成测试可以随源码交接包提供；开发期单元测试默认留在开发项目，不因“完整”而全部复制进运行交付包。
