# 文件治理：开发场景

本文件适用于代码项目的创建、开发、构建、测试和交付，必须与 `files/general.md` 一起读取。它提供九类一级目录的默认分工，但不要求每个项目机械创建全部目录。

## 一、开发场景的目标

开发项目的结构要让接手者回答四个问题：源码在哪里、如何运行和测试、哪些内容可以删除重建、交付物从哪里取得。项目大小决定地图深度和分类数量；简单项目优先少层级，复杂项目再按职责和生命周期细分。

## 二、项目初始化

新建代码项目或首次接入既有项目时，顺序固定为：

1. 检查根目录和已有入口，先读取 `files/general.md`、本文件以及目标目录入口。
2. 确认或补齐根目录 `README.md`、`AGENTS.md` 和 `CLAUDE.md`；三个文件缺一不可。
3. 在 `README.md` 建立当前实际的直接目录地图，在 `AGENTS.md` 建立规则路由。
4. 根据实际需求创建一级目录和项目维护子目录，并按各目录专用规则创建必要的说明文件；`source/` 只在其根目录保留一个 `README.md`，交付包目录按其发布接口组织。
5. 开发、测试、构建和交付结束后，执行本文件的治理验收，再报告完成。

根目录 `README.md` 面向人类，`AGENTS.md` 只负责通用 Agent 路由，`CLAUDE.md` 只负责 Claude 路由。`CLAUDE.md` 必须用相对链接指向同级 `AGENTS.md`；任何 Agent 读取 `CLAUDE.md` 后都要继续读取 `AGENTS.md`。三个入口不得互相复制正文。

## 三、九类一级目录的默认分工

一级目录只允许以下九类，按需创建，不预建空目录：

| 目录 | 放什么 | 不放什么 |
| --- | --- | --- |
| `archive/` | 退出当前流程但需保留的旧版本、旧方案和阶段归档 | 当前构建依赖、临时备份 |
| `design/` | 原型、交互流程、视觉稿、设计系统和设计令牌 | 业务源码、运行截图、构建包 |
| `build/` | 可重新生成的发布包、安装包、部署包、校验和及构建元数据 | 运行数据库、日志、缓存、唯一源文件 |
| `docs/` | 长期维护、面向人类阅读的使用、技术、决策和交付文档 | 临时报告、设计源文件、参考项目副本 |
| `reference/` | 外部项目、第三方文档、功能实现参考和样例素材 | 项目自有源码、默认运行依赖 |
| `scripts/` | 可重复执行的构建、测试、部署、迁移、校验和数据处理脚本 | 一次性实验脚本、业务源码 |
| `source/` | 项目自有正式源码和交付项目 | 完整外部上游项目、运行数据 |
| `temp/` | 可随时删除的日志、截图、缓存、实验文件和 Agent 工作文件 | 正式源码、正式测试、构建唯一输入 |
| `tests/` | 跨子项目、集成、端到端、回归、验收测试和公共测试数据 | 只属于一个模块的单元测试 |

已有老项目可以保留工具链强制目录和历史例外，但新增内容不得继续扩大旧的错误归属；迁移、删除或重命名必须有用户授权或任务必要性。

## 四、按复杂度决定层级

- 只有一个职责、一个文件或一个测试类别时，可以直接放在所属目录；按该目录专用规则决定是否需要说明文件。
- 同一目录出现多个独立职责、多个交付类型或多个测试类别时，必须建立用途分类子目录；分类目录的说明文件按该场景需要创建，不得机械复制。
- 不要为了满足形式创建空目录、空分类、时间戳层级或重复说明；目录层级必须能解释为职责边界、生命周期边界或交付边界。

## 五、各目录的专用规则

### `archive/`

作用：保存已经退出当前开发流程、但仍需长期保留的旧版本、旧方案和阶段成果。归档内容默认只读，不参与当前源码、构建、测试或运行。

说明：

- 包含多个文件的归档项必须打包为 `.zip`；只有一个文件的归档项可以保留原格式，不为压缩而压缩。
- 归档包或归档文件使用 `名称-版本-YYYYMMDD-HHmm` 命名；压缩归档的完整名称以 `.zip` 结尾。
- `archive/README.md` 是归档索引，记录当前实际存在的归档项、版本、时间和用途；它说明归档内容，不记录实时工作日志。

禁止事项：

- 不得把当前仍在开发、构建、测试或运行所需的内容放入 `archive/`。
- 不得把临时备份、实时日志或未完成材料冒充归档项。
- 不得让当前流程直接依赖归档内容，也不得把归档项散放到项目根目录或其他正式工作目录。

### `design/`

作用：存放产品设计和交互验证材料，包括需求草图、原型图、交互流程、视觉稿、设计系统、设计令牌和用于验证设计的原型代码。小型项目和大型项目只要确实有这些材料，都按本规则治理。

说明：

- 设计材料必须按明确意图和生命周期分类，例如 `research/`、`wireframes/`、`visual/`、`prototype/`、`design-system/`。
- 分类依据是材料用途，不是文件格式；图片、文档和原型代码只要服务同一设计意图，就放在同一个设计项目或分类下。
- 同一设计项目的材料不得按文件类型散落到多个目录；相关材料必须能够从同一设计目录找到。
- 只有确实存在多个独立设计意图时才创建分类目录；小项目可以少分层，但应在地图中说明边界。
- 用于验证交互的原型代码属于设计材料；正式业务源码必须放入 `source/`，运行截图和临时导出物必须放入 `temp/<任务或会话>/`。

禁止事项：

- 不得把正式业务源码、正式测试、构建包或运行数据当作设计材料存放。
- 不得按扩展名机械拆分材料，造成同一设计意图的文件散落在多个目录。
- 不得为了凑结构创建空分类、重复说明或无实际用途的深层目录。

### `build/`

作用：保存由源码和构建流程生成的发布包、安装包、部署包、校验和及构建元数据；它是可删除、可重建的构建容器，不是第二个开发项目根。

说明：

- 简单单项目默认使用 `build/<项目>-<版本>/`，直接作为交付目录；只有存在多个交付类型、发布渠道或确实需要分离的阶段时，才增加 `release/`、`checksums/`、`metadata/` 等层级。
- `build/` 是可生成的构建容器；上级项目地图已说明其可重建时，不因生成目录本身机械补 README。`build/<项目>-<版本>/` 是交付包，不是新的开发项目根。
- 每个需要说明文件的交付目录保留一份面向交付使用的 `README.md`；必须按交付场景重写，不得直接复制项目根 README。交付说明中的地图只能指向交付包内实际存在的目标。
- 交付包默认只包含运行、加载、部署、验证或发布所需文件；项目级 `AGENTS.md`、`CLAUDE.md`、开发构建脚本和内部状态默认排除。若交付类型是可继续开发的源码包，必须在交付说明中明确这一点。
- 交付目录必须能整体删除后重建，运行数据库、日志、截图、缓存和上传文件不得写入其中。

禁止事项：

- 不得把唯一源文件、运行数据库、日志、缓存或上传文件作为构建产物保存。
- 不得无理由增加 `release/` 等中间层级，也不得把交付目录伪装成新的项目根并复制整套入口文件。
- 不得让交付说明链接到交付包外不存在或未随包提供的路径。

### `docs/`

作用：存放面向人类长期维护的项目文档，包括使用、技术、构建、决策和交付说明。

说明：

- `docs/` 根目录默认只放 `README.md` 和文档主题目录；多个主题按用途分类，例如 `usage/`、`technical/`、`build/`、`decisions/`。
- 只有一个独立文档且没有分类价值时，才可直接放根部，并在 `docs/README.md` 说明理由。
- 地图只列实际存在的直接子目录或文件，路径使用可点击相对链接。

禁止事项：

- 不得把源代码、脚本、设计源文件、参考项目副本、临时报告或实时日志混入 `docs/`。
- 不得把不同主题长期散放在根部，也不得在地图中列出不存在或不可访问的路径。

### `reference/`

作用：保存项目以外的参考资料，包括完整外部项目、第三方文档、功能实现、算法、组件、接口参考和样例素材。

说明：

- 根目录只放 `README.md` 和参考分类目录；至少区分 `projects/`（完整项目）与 `implementations/`（功能、算法、组件或接口参考）。
- 完整外部项目默认放 `reference/projects/`，不得因为要运行、构建或修改就放入 `source/`。
- 保存外部资料时记录来源、版本、获取日期、许可证、用途和相对路径；能用 URL 解决的，不重复保存整份副本。

禁止事项：

- 不得把完整外部项目克隆到 `source/`，也不得把外部资料冒充项目自有源码。
- 不得让运行时默认依赖指向未经说明的参考副本，也不得保存来源或许可证不明的材料。

### `scripts/`

作用：存放可重复执行的构建、测试、部署、迁移、校验和数据处理脚本，集中承载项目自动化操作。

说明：

- 根目录默认只放 `README.md`、必要的 `AGENTS.md` 和用途分类目录；脚本按用途归类。
- 只有一个脚本且没有分类价值时，可以直接放根部，并在 `scripts/README.md` 说明理由和运行方式。
- 一次性实验脚本放入 `temp/<任务或会话>/`；可重复脚本说明输入、输出、副作用和前置条件。

禁止事项：

- 不得把业务源码、正式测试或不可重复的一次性实验长期放在 `scripts/`。
- 不得把不同职责的脚本无说明地散放，也不得隐藏未声明的外部写入、安装、删除或数据修改行为。

### `source/`

作用：存放项目自有的正式源码、可维护技术包和独立交付单元，是项目实现的唯一权威来源；`source/README.md` 是源码区唯一的局部入口，同时服务 AI 和人类。

说明：

- 项目自有正式源码只能位于 `source/` 下；一个独立交付单元通常使用 `source/<项目>/`，多个可独立构建或部署的单元再增加一层。
- `source/README.md` 说明源码区边界、直接子项目、主要入口、运行和测试方式，以及各子项目之间的关系；地图只列实际存在的直接子目录并使用可点击相对链接。
- `source/` 下的项目、技术包和源码子目录默认不重复创建 `README.md`；只有用户明确要求或子目录具有独立治理制度时，才可增加局部说明文件。
- `target/`、`node_modules/`、`out/`、`dist/` 等工具链生成目录不属于项目分类，不要求逐层人工说明，但必须可重建并纳入忽略或上级说明。

禁止事项：

- 不得把完整外部上游项目、参考副本、运行数据或临时文件放入 `source/`。
- 不得让多个项目共用无边界的源码目录，也不得把生成目录当作人工维护的源码分类。
- 不得把 `README.md` 机械复制到每个源码子项目，或让子项目说明与 `source/README.md` 的地图产生冲突。

### `temp/`

作用：保存可随时删除的日志、截图、缓存、实验文件和 Agent 工作文件，隔离不会成为正式资产的过程性材料。

说明：

- 只有确有临时内容时才创建；内容按任务或会话放入子目录，不直接散放在根部。
- 临时材料标明任务或会话边界；清空 `temp/` 不得影响项目实质内容。

禁止事项：

- 不得把正式源码、正式测试、唯一构建输入、用户数据或必须长期维护的文档放入 `temp/`。
- 正式构建、测试、运行和交付不得依赖 `temp/`；不得为了预建结构创建空目录。

### `tests/`

作用：存放跨模块或跨项目的集成、端到端、回归、验收测试和公共测试数据；单模块单元测试保留在对应源码项目内。

说明：

- 项目级 `tests/` 默认按测试性质分为 `integration/`、`e2e/`、`regression/` 或 `acceptance/` 等分类；只有一个类别且规模很小时，可以在根部直接放测试文件并在 `README.md` 说明理由。
- 只验证单个模块、不启动真实服务的单元测试，放在对应 `source/<项目>/tests/`；启动真实服务、访问真实 HTTP/API、跨模块验证完整流程或面向交付验收的测试，放项目级 `tests/`。
- 交付包是否携带测试要按交付类型判断：面向用户验收的集成测试可以随源码交接包提供；开发期单元测试默认留在开发项目，不因“完整”而全部复制进运行交付包。
- 测试目录的 `README.md` 是该目录的局部说明，不是“混入测试文件”；它应位于目录根部，负责解释分类和运行方式。

禁止事项：

- 不得把不同测试性质长期混在同一目录，也不得把说明文件散落在测试文件之间。
- 不得把单模块单元测试无理由复制到项目级 `tests/`，也不得把跨模块验收测试藏在单个源码模块内。
- 不得把运行数据、构建产物、临时报告或未声明的外部环境修改当作测试资产提交。

## 六、运行数据和外部边界

- 正式运行数据默认放独立的用户数据目录或用户明确指定的位置，不得默认写入项目根目录、`source/` 或 `build/`。
- 测试和演示数据进入系统临时目录或 `temp/<任务或会话>/`；缓存和字节码必须纳入忽略规则或配置到可重建位置。
- 项目根目录外的访问、复制、移动、修改和安装遵守全局授权；外部路径不得伪装成项目内地图或项目自有文件。

## 七、开发项目的治理验收

交付前必须对实际磁盘执行以下检查，不能只凭测试、构建或 Agent 自述：

1. 入口：根目录 `README.md`、`AGENTS.md` 和 `CLAUDE.md` 均存在且职责正确；`CLAUDE.md` 只路由到同级 `AGENTS.md`。
2. 地图：各目录按专用规则检查说明文件；`source/` 只检查根目录 `README.md`，不要求子项目重复创建；交付包目录不因本规则新增 README；每张地图只列实际直接子目录，地图和交叉引用使用可点击相对链接且目标真实存在。
3. 复杂度：没有无用途的空目录、重复说明、无理由的深层交付目录或过度拆分；每个分类都能说明其职责。
4. 落点：源码、测试、脚本、文档、参考资料、构建物、运行数据、缓存和临时物均按生命周期归位。
5. 证据：重新扫描目录并回读入口、地图和关键链接；任一项无法证明时，不得报告项目完成。
6. 交付物：构建完成后单独扫描每个交付目录，确认交付类型、文件清单、README 内容、链接目标和校验文件彼此一致；不得只验收开发项目根。

## 八、规范保护

本文件由用户维护。除非用户明确要求，Agent 不得修改、移动、删除、压缩或放宽本文件；发现需求与规范冲突时先报告冲突和影响。
