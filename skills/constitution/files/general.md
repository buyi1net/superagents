# 文件治理：通用原则

本文件适用于所有涉及读取、创建、修改、移动、重命名或删除文件的任务。它不限定技术栈，目的是让没有历史对话的 Agent 理解文件的归属、用途、位置、生命周期和可删除条件。

## 一、治理意图

文件治理只追求六个结果：

- 可导航：人类和 AI 都能从合适层级的入口、地图和说明文件找到实际内容。
- 可归类：文件按用途、职责和生命周期落在明确的目录边界内，不与无关内容混放。
- 可维护：保持目录整洁、层级适度，文件不散落、不重复、不堆放无关内容，说明文件和地图保持一致。
- 可归属：每个文件都有明确的长期用途、责任边界和必要的说明来源。
- 可重建：生成物、缓存和临时物可以删除后重新产生，正式流程不依赖唯一过程文件。
- 可交接：项目结构、目录职责和工作入口不依赖口头说明或历史会话。

目录和说明文件不是为了满足模板形式。每次创建人工维护的目录或文件，都要能说明它解决了什么长期问题；不能为了满足条款而创建空分类、重复说明或无用途的层级。

## 二、先理解边界，再写入

新增、移动或恢复文件前，依次判断：

1. 它是项目自有文件、外部资料、运行数据、生成物，还是临时物？
2. 它属于开发项目根、构建暂存根、交付包根，还是运行实例根？
3. 它是否有独立职责、独立用途或独立生命周期？
4. 读者是否需要从地图或说明文件进入它？
5. 它能否由源码、脚本或工具重新生成？
6. 根据判断结果选择目录、说明文件、入口和生命周期；不能确定时暂停写入并报告。

本文件的明确条款优先于语言、框架、工具链或开源项目的常见惯例。用户要求与通用规则冲突时，用户要求可以形成例外，但 Agent 必须记录被覆盖的规则、例外范围、适用对象、生命周期和恢复条件，不得把例外写成通用规则。

## 三、术语

- 开发项目根：存放源码、文档、脚本、测试和其他人工维护内容的项目边界；默认是读取、搜索、执行和写入的工作根。
- 构建暂存根：由构建流程产生、可整体删除并重新生成的目录；不作为运行实例使用。
- 交付包根：按明确交付类型组织、会被直接分发、加载或交接的目录；它不自动等同于开发项目根。
- 运行实例根：从交付包取得并实际运行的目录；可以有按规则生成的运行数据，但不应反向修改开发项目或构建暂存根。
- 人工维护目录：承载长期内容或独立工作职责、需要人或 Agent 主动维护的目录。
- 生成目录：由工具链产生、可整体删除后重建的目录，例如 `target/`、`node_modules/`、`dist/`。
- 运行数据：程序运行后产生并需要持续保留或管理的数据库、用户数据和上传文件；日志、缓存和进程文件只有在需要持续管理时才属于运行数据。
- 临时文件：清空后不影响项目实质内容的日志、截图、下载文件、缓存、中间文件、实验文件和 Agent 工作文件。
- 交付包目录：交付包根及其内容目录；目录内文件受交付格式约束，不等同于开发项目资料目录。
- 导航引用：地图、索引、职责表、正文交叉引用和用于引导读者进入目录或文件的目录树。
- 命令示例：只展示命令语法、参数或示例输入的内容；其中的路径是参数，不承担项目导航功能。

## 四、目录、内容和生命周期

- 目录只在有实际内容或已确认职责时创建；不得预建空目录、空分类或无用途的层级。
- 一个目录应有一个明确的主职责、项目边界或生命周期；文件按用途、职责和生命周期归类，不按扩展名机械堆放。
- 同一任务或独立职责的材料应集中存放；多个独立职责长期共存时，必须按用途、项目、测试性质或生命周期拆分。
- 同一一级目录下存在两个或以上独立主题、用途或生命周期时，必须建立二级分类目录。一级目录根部原则上只保留 `README.md`、必要入口和实际存在的分类目录；内容文件不得继续直接散放在根部。
- 只有一个主题、一个用途且规模很小的目录，才可以在根部直接放内容文件；必须在 README 中说明不拆分的理由。
- 文档按主题归类，脚本按操作用途归类，测试按测试性质和范围归类，设计材料按设计意图归类。
- 说明文件放在它所说明的内容边界内，与被说明内容并列；说明文件、日志、报告、截图、缓存、构建物和临时物不得互相混放。README 不属于内容文件，但不得为了让每个目录都有说明而机械创建。
- 人工维护目录或其直接内容发生新建、删除、移动、重命名、职责变化或入口变化时，必须同步更新受影响的最近上级地图；如果该地图由一级目录 README 承载，就同步更新对应 README。只修改文件正文且没有改变目录职责、入口或地图内容时，回读确认地图仍然准确，无需机械改写。
- 每个目录的地图只记录当前实际存在、对读者有导航价值的直接子目录或文件；不把制度允许但尚未创建的内容写成当前结构。
- 地图按目录逐级维护：小项目不必展开到文件级，大项目由各级说明文件维护自己的直接内容；根目录不得用一张整棵文件树替代下级说明。
- 生成物和缓存应可重建；临时物应可删除；运行数据不得成为正式源码或构建暂存根的唯一依赖。它们可以根据工具链要求放在特殊位置，但必须与人工维护内容区分。

## 五、说明文件、地图和链接

- 项目根目录和实际创建并承载内容的一级目录统一使用 `README.md` 作为唯一目录说明入口；创建一级目录时先建立 README，再写入正式内容，缺少 README 时目录治理未完成。
- 二级及更深目录不得新增 `README.md`，不要求为每个目录、每个参考项、每个归档项或每个实现文件单独建立 README；外部完整项目原本自带的 README 可以随外部资料保留，但不属于本项目新增的目录说明，也不得复制或仿照扩散。不能以“目录存在”“内容较多”或“方便说明”为理由新增深层 README；发现这类机械 README 应视为过度创建并在验收中记录。
- README 的最低内容是：所在层级的作用、边界、实际直接内容，以及必要的使用方法、运行方式或进入路径。README 是导航和职责说明，不是完整文件清单、实时日志、动态状态表或测试统计。
- 源码区的一级目录说明固定使用 `source/README.md`；其他一级目录按同一规则使用各自根部的 `README.md`。同一职责只保留一个主要说明来源，不得机械复制或让上下级说明互相冲突。
- 支持超链接的格式中，导航引用的项目内文件或目录必须使用可点击的相对链接，且目标实际存在。导航引用包括项目地图、目录索引、文件职责表、正文中的“见某文件”和用于进入交付目录的路径。
- 代码块目录树只能作为辅助示意，不能作为唯一地图；真正的地图必须由可点击目录条目或列表提供。命令示例中的路径可以使用代码格式，但不能代替项目地图。
- 外部资源使用完整 URL；不支持超链接的格式至少写出相对于项目根目录的路径。

## 六、入口职责和保护

- 代码项目根目录必须同时有 `README.md`、`AGENTS.md` 和 `CLAUDE.md` 三个入口。
- `README.md` 面向人类，负责项目说明、当前实际地图、启动方式和必要的使用信息；它不是制度或 Agent 路由的唯一来源。
- `AGENTS.md` 面向 Agent，只负责指向适用规则和其他入口；不得写项目状态、测试数量、交付日志或完整文件清单。项目专用约定应放在专门的规则或说明文件中，并从 `AGENTS.md` 路由到它。
- `CLAUDE.md` 只保留固定提示“读取同级 `AGENTS.md`。禁止在此文件写入内容。”和指向同级 `AGENTS.md` 的可点击相对链接；不得增加规则、状态、地图或工作记录。读取 `CLAUDE.md` 后必须继续读取 `AGENTS.md`。
- 入口文件之间不得复制同一份正文；规则只有一个来源，项目说明只有一个主要来源，动态状态不得当作长期地图。

## 七、运行实例、外部资料和交付包

- 开发项目中的正式运行数据默认放在独立的用户数据目录或用户明确指定的位置，不得写入开发项目根、正式源码目录或构建暂存根。
- 测试和演示数据进入系统临时目录或项目的 `temp/<任务或会话>/`。一次性日志、截图和缓存按临时物处理；需要持续保留或管理的内容按运行数据处理。
- 便携式离线交付包可以在解压后的运行实例根生成 `data/` 等运行数据目录，但该目录必须在交付说明中标明为运行数据，不得进入初始交付包或构建暂存根。
- 运行实例的日志、缓存、锁和进程文件必须放在运行数据边界内；测试应使用独立数据目录和端口，并在结束后停止进程、释放端口、回收临时文件。
- 生成物和缓存必须纳入忽略规则或配置到可重新生成的位置；正式流程不得依赖临时目录或生成目录中的唯一文件。
- 外部资料、上游项目和第三方副本必须与项目自有文件区分；不得因为它会被查看、修改或构建就将其当作自有文件。
- 交付包只保留与其交付类型相关的加载、运行、部署、验证或发布文件；不得为了补地图、职责说明或形式完整而添加日志、状态或其他非接口文件。

## 八、交付类型和构建证据

- 构建前必须声明交付类型：可运行包、完整源码交接包，或其他明确类型。交付说明必须写明使用者、内容边界和是否包含完整源码、测试与开发脚本。
- 遵循九类开发一级目录的项目中，构建暂存统一放在 `temp/build/`；`build/` 一级目录只保留已经确认可交付的最终交付物，不得把构建暂存、半成品或待验证包放进去。
- 交付目录和 ZIP 同时存在时，二者必须来自同一份文件清单；如果目录只是打包暂存，应放在 `temp/build/`，不得冒充 `build/` 下的最终交付物。
- 每个最终交付包必须随附使用说明、更新日志和校验信息；这些文件可以位于交付包内部或其同级交付目录中，但必须和该交付包一一对应。地图只能指向实际存在的目标，不得直接复制开发项目根 README。
- 交付包必须能整体删除后重建；运行数据库、日志、截图、缓存、上传文件和 `__pycache__` 不得进入 `temp/build/` 或初始交付包。
- 任何运行验证都应在解压副本或临时副本中执行。验证结束后重新扫描原构建暂存根、交付目录和 ZIP，确认文件清单、校验文件和目录结构未被运行过程改变。

## 九、变更与证据

- 修改文件前重新读取当前内容，确认没有并行改动；优先精准修改，不得使用旧版本整体覆盖。
- 文件结构变更后重新扫描受影响目录，回读入口、地图和链接；发现不一致先查明来源，不能擅自覆盖他人改动。
- 交付或报告完成前，必须用实际磁盘扫描和文件回读证明入口、地图、分类、链接和落点正确；测试通过或 Agent 自述不能替代治理证据。
- 验收必须同时检查开发项目根、构建暂存根、交付包根和运行实例副本；不能只验收其中一个边界。
- 必须记录测试、构建和运行过程对项目外文件、进程、端口、服务、环境变量和用户配置的影响；未经授权的外部变化视为未完成。
- 校验和文件必须能在目标环境直接验证，不能因为平台不兼容的行尾或路径格式导致命令失败。

## 十、规范保护

本文件由用户维护。除非用户明确要求，Agent 不得修改、移动、删除、压缩或放宽本文件；发现需求与规范冲突时先报告冲突和影响。
