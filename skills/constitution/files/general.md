# 文件治理：通用原则

本文件适用于所有会读取、创建、修改、移动、重命名或删除文件的任务。它不规定某一种技术栈，而是保证陌生 Agent 在没有历史对话的情况下，也能理解文件为什么放在那里、如何找到它、何时可以删除它。

## 一、治理目标

文件治理只追求六个结果：

- 可导航：人类和 AI 都能从合适层级的入口、地图和说明文件找到实际内容。
- 可归类：文件按用途、职责和生命周期落在明确的目录边界内，不与无关内容混放。
- 可维护：保持目录整洁、层级适度，文件不散落、不重复、不堆放无关内容，说明文件和地图保持一致。
- 可归属：每个文件都有明确的长期用途、责任边界和必要的说明来源。
- 可重建：生成物、缓存和临时物可以删除后重新产生，正式流程不依赖唯一过程文件。
- 可交接：项目结构、目录职责和工作入口不依赖口头说明或历史会话。

目录和说明文件不是为了凑齐模板；每次创建目录或文件，都要能说明它解决了什么长期问题。

## 二、先判断，再落盘

新增、移动或恢复文件前，按以下顺序判断：

1. 它是项目自有文件、外部资料、运行数据、生成文件，还是临时文件？
2. 它是否需要长期维护，是否属于某个独立项目或职责？
3. 它是否需要被读者导航到？
4. 它能否由源码、脚本或工具重新生成？
5. 根据上述答案选择目录、说明文件和入口；不能确定时暂停写入并报告。

本文件的明确条款优先于语言、框架、工具链或开源项目的常见惯例。

## 三、术语

- 项目根目录：当前任务默认的读取、搜索、执行和写入边界；根目录外内容不自动纳入项目地图。
- 人工维护目录：承载长期内容或独立工作职责、需要人或 Agent 主动维护的目录。
- 生成目录：由工具链产生、可整体删除后重建的目录，例如 `target/`、`node_modules/`、`dist/`。
- 运行数据：程序运行后产生或持续更新的数据库、用户数据、日志、缓存、上传文件和截图。
- 临时文件：清空后不影响项目实质内容的日志、截图、下载文件、实验文件和 Agent 工作文件。
- 交付包目录：按插件、库、安装包或其他发布接口组织、会被直接分发或加载的内容目录；目录内文件受交付格式约束，不等同于项目资料目录，也不自动等同于开发项目根目录。
- 导航引用：地图、索引、职责表、正文交叉引用和用于引导读者进入目录或文件的目录树。
- 命令示例：只展示命令语法、参数或示例输入的代码；其中的路径是参数，不承担项目导航功能。

## 四、目录说明和地图

- 目录只在有实际内容或已确认职责时创建；不得预建空目录、空分类或无用途的层级。各场景规则只补充例外，不重复定义这条总原则。
- 项目维护目录的说明文件按“说明文件治理”决定；不因创建目录就机械增加 README。交付包目录按发布接口处理。
- 新建、移动或重命名项目维护目录时，必须同步更新最近上级地图；是否新增局部说明文件按“说明文件治理”判断。删除目录时同步更新上级地图。
- 每个目录的地图只记录当前实际存在、对读者有导航价值的直接子目录；不把制度允许但尚未创建的目录写成当前结构。
- 地图按目录逐层接力：小项目不必展开到文件级，大项目由各级说明文件维护自己的直接子目录；根目录不得用一张整棵文件树替代下级说明。
- 只有生成目录、版本控制目录和纯缓存目录可以免于人工维护 `README.md`；上级说明必须标明它们可重建或可删除。
- 交付包目录只保留加载、构建或发布所需文件；不得为了补地图、职责说明或形式完整而添加 README、日志、状态或其他非接口文件。
- 交付包生成前必须先确定交付类型和使用者；交付包的 README（如接口需要）只说明如何取得、运行、验证或集成交付物，不得直接复制项目根 README。
- 项目根的 `AGENTS.md`、`CLAUDE.md`、开发脚本、单元测试和内部状态默认不属于交付包；只有交付接口明确需要，或交付包本身就是可继续开发的源码包时，才可纳入并在交付说明中说明原因。

## 五、说明文件治理

- 根目录入口按“入口职责”分工；普通项目维护目录的说明文件默认使用 `README.md`。
- 项目根下的一级目录不因创建目录就机械增加 README；二级目录是说明文件的默认粒度，承载独立职责、独立项目或一组需要被导航的内容时通常在目录根部放置一个 README。只有简单、内容很少且上级地图足以说明的二级目录，才可以不单独创建。
- 不是每个目录都必须有说明文件。重要子项目、大型项目拆分单元、独立运行单元或拥有独立生命周期的更深层目录，可以酌情增加 README；生成目录、纯缓存目录和交付包目录按各自规则处理。
- README 同时服务 AI 和人类，至少说明本目录作用、边界、实际直接内容、必要的使用或进入方式；只维护本目录，不重复上级正文。
- README 是导航和职责说明，不是实时日志、动态状态表、测试计数器或完整文件清单；动态信息应放在明确的状态或报告文件中。
- 说明文件中的地图、索引和交叉引用必须只指向实际存在的目标，并使用可点击的相对链接；不能用制度模板或示例结构冒充当前目录地图。
- 同一职责只保留一个主要说明来源；不得机械复制 README，也不得让上下级说明维护互相冲突的地图。

## 六、目录内容治理

- 一个目录应有一个明确的主职责、项目边界或生命周期；文件按用途、职责和生命周期归类，不按扩展名机械堆放。
- 同一任务或同一独立职责的材料应集中存放；多个独立职责长期共存时，必须按用途、项目、测试性质或生命周期拆分。
- 说明文件放在所属目录根部，与被说明的内容并列；日志、报告、截图、缓存、构建物和临时物不得混入正式内容区。
- 文档按主题归类，脚本按操作用途归类，测试按测试性质和范围归类，设计材料按设计意图归类；这些是本原则在不同场景下的具体表现。
- 不得为了形式创建空分类、重复目录、时间戳层级或无实际用途的深层目录；已有分类必须能从目录内容中解释其职责。
- 生成物、缓存、运行数据和临时物可以有工具链要求的特殊落点，但必须与人工维护内容区分，并且可重建、可删除或不被正式流程依赖。

## 七、入口职责

- 代码项目根目录必须同时有 `README.md`、`AGENTS.md` 和 `CLAUDE.md` 三个入口；这是为了保证人类、通用 Agent 和 Claude 都能从同一项目边界开始工作。
- `README.md` 面向人类，负责项目说明、当前实际地图、启动方式和必要的使用信息；它不是制度或 Agent 路由的唯一来源。
- `AGENTS.md` 面向 Agent，只负责路由到适用规则和入口；不得写项目状态、测试数量、交付日志或完整文件清单。
- `CLAUDE.md` 面向 Claude，只能用相对链接指向同级 `AGENTS.md`，不得维护第二套规则、地图或状态。读取 `CLAUDE.md` 后必须继续读取 `AGENTS.md`。
- 入口文件之间不得复制同一份正文；规则只有一个来源，项目说明只有一个主要来源，动态状态不得伪装成长期地图。

## 八、导航引用和链接

- Markdown 等格式支持超链接时，导航引用中的项目内文件或目录必须使用可点击的相对链接，且目标实际存在。
- 导航引用包括项目地图、目录索引、文件职责表、正文中的“见某文件”和用于进入交付目录的路径。
- 命令、参数、示例输入和数据值中的路径可以使用代码格式；但命令示例不能代替项目地图，也不能把导航路径伪装成参数。
- 代码块目录树只能作为辅助示意，不能作为唯一地图；真正的地图必须由可点击目录条目或列表提供。
- 外部资源使用完整 URL；不支持超链接的格式至少写出项目根内相对路径。

## 九、运行数据、生成物和临时物

- 运行数据不是源码、文档或构建产物；不得默认写入项目根目录、正式源码目录或可重新生成的交付目录。
- 日志、截图、下载文件、中间文件、缓存、实验产物和 Agent 工作文件进入系统临时目录或项目的 `temp/<任务或会话>/`，不得直接散放在项目根或 `temp/` 根部。
- 生成物和缓存必须纳入忽略规则或配置到可重新生成的位置；正式流程不得依赖临时目录或生成目录中的唯一文件。
- 外部资料、上游项目和第三方副本必须与项目自有文件区分；不能因为它会被查看、修改或构建就冒充自有文件。

## 十、变更与证据

- 修改文件前重新读取当前内容，确认没有并行改动；优先精准修改，不用旧版本整体覆盖。
- 文件结构变更后重新扫描受影响目录，回读入口、地图和链接；发现不一致先判断来源，不能擅自覆盖他人改动。
- 交付或报告完成前，必须用实际磁盘扫描和文件回读证明入口、地图、链接和落点正确；测试通过或 Agent 自述不能替代治理证据。
- 构建生成交付包后，必须把交付包当作独立边界重新验收：回读其入口和说明，检查所有导航链接的目标，核对文件清单与交付类型，确认没有把项目根专用路径、开发工具、内部状态或临时物带入其中。

## 十一、规范保护

本文件由用户维护。除非用户明确要求，Agent 不得修改、移动、删除、压缩或放宽本文件；发现冲突时先报告冲突和影响。
