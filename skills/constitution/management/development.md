# 开发场景文件治理规范

本文件适用于代码项目的创建、开发、构建、测试和交付，必须与 [general.md](general.md) 一起读取。它只补充开发项目的一级目录职责，以及源码、测试、设计、文档、构建和交付的专用边界。

## 一、开发场景的目标

开发项目的结构要让接手者找到源码、运行和测试方式、可删除后重建的内容，以及交付物的取得位置。目录索引深度和分类数量应根据项目规模、职责数量和读者导航需要确定；简单项目优先少层级，复杂项目再按职责和生命周期细分。

## 二、项目初始化

新建代码项目或首次接入既有项目时，建议按以下顺序执行：

1. 检查根目录和已有入口，先读取 [general.md](general.md)、本文件以及目标目录中已有的入口文件。
2. 按通用入口规则确认或补齐项目根入口文件。
3. 在项目根说明入口建立当前实际的直接目录索引，在 Agent 入口建立规则路由；只创建实际需要的一级目录和维护子目录。
4. 明确项目是开发项目、构建暂存根、交付包还是运行实例，不让同一目录同时承担互相冲突的生命周期。
5. 开发、测试、构建和交付结束后，执行通用治理验收以及本文件的目录专用检查，再报告完成。

## 三、九类一级目录的默认分工

新增人工维护一级目录优先使用以下九类；是否创建由实际任务内容决定。现有项目的工具链目录和稳定使用的其他目录可以保留；确有独立职责且不适合现有分类时，可以增加其他一级目录，并在根 README 中说明原因。

| 目录 | 放什么 | 不放什么 |
| --- | --- | --- |
| `archive/` | 已废弃、退出当前流程但仍需保留的旧方案、旧版本和阶段成果 | 当前构建依赖、临时备份、未完成工作 |
| `design/` | 原型图、交互原型及 UI 设计系统 | 架构文档、技术文档、普通项目文档、业务源码、运行数据、构建包 |
| `build/` | 已确认可交付的最终交付包、安装包、部署包及其随包提供的使用说明、更新日志和校验文件 | 构建暂存、半成品、待验证包、运行数据库、日志、缓存、开发侧唯一源文件和开发项目说明 |
| `docs/` | 项目全部长期维护的使用、技术、架构、决策、计划和交付文档 | 视觉设计源文件、业务源码、参考项目副本、临时报告 |
| `reference/` | 外部项目、第三方文档、功能实现参考和样例素材 | 项目自有源码、默认运行依赖 |
| `scripts/` | 可重复执行的构建、测试、部署、迁移、校验和数据处理脚本 | 业务源码、正式测试、一次性实验脚本 |
| `source/` | 项目自有正式源码和独立交付单元 | 完整外部上游项目、运行数据、临时文件 |
| `temp/` | 可随时删除的日志、截图、缓存、实验文件和 Agent 工作文件 | 正式源码、正式测试、构建唯一输入 |
| `tests/` | 跨子项目、集成、端到端、回归、验收测试和公共测试数据 | 只属于一个模块的单元测试 |

既有项目可以保留工具链强制目录和稳定的历史结构；新增内容不得继续扩大已有但不符合当前分类边界的归属。迁移、删除或重命名必须有用户授权或明确的任务必要性，并在变更记录中说明影响。

一级目录的通用分类、说明文件、运行数据、生成物、临时物、交付类型和证据规则以 [general.md](general.md) 为准；以下内容只补充开发目录的专用边界。

## 四、各目录的专用规则

### `archive/`

作用：保存已经废弃、退出当前开发流程、但仍需长期保留以便追溯的旧版本、旧方案和阶段成果。归档内容默认只读，不参与当前源码、构建、测试或运行。

边界：

- 归档项可以使用版本化目录或 `.zip`；需要整体分发、冻结或长期只读保存时使用 `.zip`。只有一个文件的归档项可以保留原格式。
- 归档包或归档文件使用 `名称-版本-YYYYMMDD-HHmm` 命名；时间使用执行归档时的本地时间，压缩归档的完整名称以 `.zip` 结尾。
- 归档索引或统一记录文件记录当前实际存在的归档项、版本、时间、用途、归档原因、被替代的方案或版本、替代决策以及当前是否仍可恢复；不要求在每个归档目录内新增 README。
- 当前仍在开发、构建、测试或运行所需的内容、临时备份、实时日志和未完成材料不得放入 `archive/`，当前流程也不得依赖归档内容。

### `design/`

作用：只存放原型图、交互原型和 UI 设计系统。设计资料按设计意图归类，不按文件格式拆散。

边界：

- 可以包含页面原型、交互流程、原型图、设计系统、设计令牌、组件规范和原型验证资料；原型验证代码只能服务于原型，不得成为正式业务源码。
- 同一设计意图的相关材料应放在同一设计目录；存在两个及以上独立设计意图时，建立二级分类目录，例如 `prototype/`、`ui-system/`。
- 架构、数据模型、技术选型、实施计划、用户手册、研究记录和交付说明属于 `docs/`，不属于 `design/`；正式业务源码放入 `source/`。
- 正式业务源码放入 `source/`；运行截图和临时导出物放入 `temp/<任务或会话>/`。

### `build/`

作用：只保存已经确认可交付的最终交付目录、发布包、安装包、部署包及其随包提供的使用说明、更新日志和校验文件。它不是开发项目根，也不是运行实例根；开发侧交付说明放在 `docs/`，构建暂存统一放到 `temp/build/`。

边界：

- 单一且规模较小的项目可以使用 `build/<项目>-<版本>/`；只有存在多个交付类型或发布渠道时，才增加有实际内容的分类层级。构建阶段不得把 `build/` 当作暂存工作区。
- 构建前必须在 README 或交付说明中记录交付类型。可运行包与完整源码交接包的内容边界不同，必须在交付说明中写明面向对象和包含范围。
- 交付目录和 ZIP 同时存在时，二者必须来自同一份逻辑文件清单；待打包目录、半成品和待验证目录必须留在 `temp/build/`，不得出现在 `build/`。
- 每种最终交付物必须有对应的使用说明、更新日志和校验信息，并说明交付类型、适用环境、入口、运行方式、验证命令以及是否包含完整源码。开发项目的构建、发布和重建方法写入 `docs/` 下的交付说明；交付目录内的说明只描述当前交付物，不得把开发项目根当成交付包根，也不得索引交付包中不存在的 `tests/`、`scripts/`、`temp/`、`build/` 或开发项目外部路径。
- `build/` 中的交付目录和压缩包不得在其中直接开发或修改；存在运行验证时，应在解压副本或临时副本中执行，验证后复查 `build/` 内交付物未被运行过程改变。
- `__pycache__`、运行数据库、日志、截图、缓存、锁、进程文件、上传文件和其他运行时生成缓存不得进入 `temp/build/` 或初始交付包。
- 交付包说明只说明如何获取、运行、验证或集成交付物，不复制开发项目根说明；一级交付目录的说明只负责当前实际交付物索引。

### `docs/`

作用：存放整个项目的长期维护文档，面向项目使用者和接手项目的 Agent。`docs/` 是人类参与最多的文档区，其 README、目录索引、标题、正文、表格、状态和摘要统一使用简体中文；新建目录和文件名默认使用简体中文，代码标识、命令、路径、URL、产品名和技术缩略词按原文保留。

边界：

- 可以包含用户说明、技术说明、架构说明、数据格式、实施计划、决策记录、构建说明、交付说明和运维说明等。
- `docs/` 根部原则上只放目录说明文件和实际存在的文档主题目录，例如 `使用说明/`、`技术说明/`、`架构设计/`、`决策记录/`、`交付说明/`。`docs/README.md` 面向人类提供按阅读目的组织的主要入口，不得只把文件夹名称重新列一遍；需要给 Agent 选择上下文时，由 `docs/AGENTS.md` 或其他明确的路由文件负责。
- 存在两个及以上独立文档主题时，必须建立二级分类目录；只有一个主题且规模很小时，才可以直接放在根部，并在 `docs/` 的一级目录说明中说明理由。
- 新建二级目录、文档标题和面向人类的说明必须使用简体中文；既有英文路径可以保留，除非另有迁移任务并完成链接和交付边界验证。不得用目录名掩盖主题混放。
- 视觉设计源文件和交互原型放入 `design/`；临时报告和实时日志放入 `temp/<任务或会话>/`。

### `reference/`

作用：保存项目以外的参考资料，包括完整外部项目、代码实现参考、第三方文档、标准、算法、组件、接口参考和样例素材。

边界：

- 根部只放目录说明文件和实际存在的参考分类；完整参考项目统一归入 `reference/projects/`，代码实现参考统一归入 `reference/implementations/`，其他类型再按实际用途增加分类。
- 不为不存在的参考类型创建空目录；只有一种参考类型且规模很小时，可以直接放在根部，并在一级目录说明中说明理由。
- 完整外部项目默认放 `reference/projects/`，不得因需运行、构建或修改而放入 `source/`。
- 完整参考项目和代码实现参考分别维护各自类别的收录标准、目录索引和记录格式；两类参考项不得共用含义不清的说明模板。相关记录统一放在 `reference/` 的 README、索引文件或项目 `docs/` 中，不在每个参考目录内新增 README。
- 每个参考项必须有说明记录，包含来源、完整外部 URL、版本或提交、获取日期、许可证、用途和参考范围。保存本地副本时记录项目内相对路径；代码实现参考还要说明关键实现入口、技术栈、可借鉴点和限制。
- 保存外部资料时优先记录完整 URL；只记录 URL 且已足够满足使用目的时，不重复保存整份副本。
- 运行配置不得默认依赖未记录来源的参考副本，也不得保存来源或许可证不明的材料。

### `scripts/`

作用：存放可重复执行的自动化脚本。

边界：

- 脚本按操作用途归类，例如 `runtime/`、`test/`、`build/`、`data/`、`deploy/`；存在两个及以上独立用途时必须建立二级分类目录。
- 根部只保留目录说明文件、必要的 `AGENTS.md` 和实际存在的用途分类目录；只有一个脚本且没有分类价值时，才可以直接放在根部，并在一级目录说明中说明理由和运行方式。
- 可重复脚本必须在 `scripts/` 的 README、索引或项目 `docs/` 中说明输入、输出、副作用和前置条件；一次性实验脚本放入 `temp/<任务或会话>/`。
- 不得把业务源码、正式测试或不可重复的一次性实验长期放在 `scripts/`，也不得隐藏未声明的外部写入、安装、删除或数据修改行为。

### `source/`

作用：存放项目自有的正式源码、可维护技术包和独立交付单元，是项目实现的主要维护来源；源码区必须有一级目录总览说明。

边界：

- 新建项目的正式源码默认位于 `source/` 下；一个独立交付单元通常使用 `source/<项目>/`，多个可独立构建或部署的单元可使用 `source/<类别>/<项目>/`。既有项目可以保留已稳定使用的源码根，除非任务明确要求迁移并完成构建、测试和入口验证。
- 源码区一级目录总览必须说明源码区边界、实际直接子项目、每个子项目的主要职责、主要入口，以及适用的运行和测试方式；即使只有一个子项目也不能省略。
- 总览只描述直接子项目、公开入口和职责边界，不逐个解释实现文件、函数和类，也不维护完整文件清单。
- 直接子项目、重要技术包或大型拆分单元需要额外说明时，应使用源码区 README、项目 `docs/` 或已有索引文件，不得机械创建深层目录说明。
- `target/`、`node_modules/`、`out/`、`dist/` 等工具链生成目录不属于源码分类，不要求逐层人工说明，但必须可重建并纳入忽略规则或上级说明。
- 不得把完整外部上游项目、参考副本、运行数据或临时文件放入 `source/`，也不得让多个项目共用无边界的源码目录。

### `temp/`

作用：存放可随时删除、可重新产生且不构成项目正式内容的构建暂存、测试临时物、实验文件、一次性日志、截图、缓存和 Agent 工作文件。需要长期保留的审计证据、交接材料或测试基线不得仅因暂时由 Agent 生成就放入这里。

边界：

- 临时区一级目录说明必须写清临时区边界、实际存在的分类、生命周期和清理责任；不存在临时区时不得为了补说明而创建空目录，不能用实时日志代替说明。
- 构建暂存统一放在 `temp/build/`；测试临时数据和运行副本按任务或会话归入 `temp/<任务或会话>/`，不得把不同生命周期的内容长期混放在 `temp/` 根部。
- 临时内容必须可删除且可重新产生；需要长期保留的方案、文档、源码、测试基线和交付物分别归入 `archive/`、`docs/`、`source/`、`tests/` 和 `build/`。
- 清理临时内容前确认没有被正式源码、构建流程、测试命令或交付包作为唯一依赖；不得把 `temp/` 变成未声明的运行数据目录或长期备份区。

### `tests/`

作用：存放跨模块或跨项目的集成、端到端、回归、验收测试和公共测试数据；单模块单元测试保留在对应源码项目内。

边界：

- 测试区一级目录说明必须写清测试区边界、实际测试分类、运行命令、测试数据、端口或服务依赖、产物位置和清理/保留规则；没有对应内容时明确写“无”，不能只依赖项目根说明或测试脚本中的注释。
- 项目级 `tests/` 按测试性质分为实际存在的分类，例如 `integration/`、`e2e/`、`regression/` 或 `acceptance/`；只有一个类别且规模很小时，才可以在根部直接放测试文件，并在测试区一级目录说明中说明理由。
- 只验证单个模块且不启动真实服务的单元测试，放在对应 `source/<项目>/tests/`；启动真实服务、访问真实 HTTP/API、跨模块验证完整流程或面向交付验收的测试，放项目级 `tests/`。
- 面向用户验收的集成测试可以随源码交接包提供；开发期单元测试默认留在开发项目，不因“完整”而全部复制进运行交付包。
