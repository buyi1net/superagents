# 参考材料治理规范

> 把项目使用的外部参考材料分类保存，让用户和 Agent 能从一个入口知道有哪些材料、为什么保留、在哪里、当前是什么状态，并能继续维护。
>

## 收录边界

放入参考材料目录：

- 外部收集，只用于理解、研究、比较、核验、举证、学习或借鉴的材料；
- 外部项目、制度、标准、文献、数据、模板、方法、素材、案例和样例；
- 正式输入或外部组成部分的说明、快照和分析记录，只承担参考或证据职责时也可以收录。

不放入参考材料目录：

- 项目正在产出或长期维护的自有成果、过程记录、正式数据、交付内容和运行内容；
- 当前工作需要直接采用、编辑、加工、执行或随成果交付的正式输入与外部组成部分。

识别参考材料看用途，不看目录名称，也不看用户是否说出“参考材料”。

## 目录与分类

```text
<参考目录>/
├── README.md          # 人类阅读与查找入口
├── AGENTS.md          # Agent 维护入口
├── CLAUDE.md          # Claude Code 专用入口
└── <分类名称>/
    └── <参考项名>/
        ├── <说明文件>   # 如「参考说明.md」
        └── ...
```

**参考目录：**

- 作为项目一级目录，目录名称优先使用同级现有文件夹的语言和命名风格，哪怕同级文件夹是空的。
- 如果没有可参照内容时，再按项目主要语言判断，不以当前对话语言判断。
- 后续可以根据项目的实际情况选走是否重命名为“参考资料”或者“reference”(比如用户要求整理资料的时候)。

**分类名称：**

- 分类名称使用用户在本项目中的主要交流语言。
- 已有分类时沿用现有语言，后续新增分类不得因单次对话语言变化而切换。
- 分类名称按材料在当前项目中的实际用途确定，例如核心依据、流程范例、竞品项目、视觉参考和其它参考；这些名称只是示例，不是固定目录。
- 同类材料使用同一分类；跨类材料按主要用途归类，次要用途写入参考说明。

**参考项名：**

- 每个参考项单独建立文件夹，名称优先使用来源原名，不翻译。
- 每个参考项都必须分类，只有一个参考项也不能直接散放在参考目录根部。

**其它事项：**

- 用不到的分类不创建，不预建空目录。
- 已有合理分类继续沿用。用户要求整理时可以按本规范重新分类；未获授权不得随意迁移或改名。

## 参考说明

每个参考项建立一份说明文件，与本地存档放在同一个参考项文件夹中。说明文件不要命名为 `README.md`，避免与外部项目自带的 README 冲突；中文项目可用`参考说明.md`。该文件不追求信息的大而全，只追求人类和其它 Agent 快速看懂和不撑爆小窗口模型的上下文。

## README.md

`README.md` 是给人类阅读的统一入口，只写当前目录的实际内容和查找信息，不承担 Agent 操作手册职责，也不照抄本规范。文件开头应提醒 Agent 修改本目录前先读可点击的 `AGENTS.md` 链接，禁止无差别读取全部项目，避免占用上下文。

**基本要求：**

1. 当前实际分类及其用途(表格)；
2. 按分类排列的参考索引(固定写三行)。

```md
### 核心上游

**项目：**cordis
**价值：**DSH 底层插件框架，第一方插件开发的编程载体。
**入口：**[参考说明](核心上游/cordis/参考说明.md) · [本地存档](核心上游/cordis/) · `8cc9e33f` · 来源：[GitHub](https://github.com/cordiverse/cordis)· 开源协议类型 · 索引时间：2026-08-14 13:15
```

**维护原则：**

- 实际分类列要使用可点击的相对文件夹链接。
- “价值”用一句话说明为什么保留，让读者不用打开说明文件也能判断是否相关。
- “入口”依次提供参考说明、本地存档和信息来源；项目内链接使用可点击的相对链接。
- 有本地存档时要使用可点击的相对文件夹链接，而非文件连接。
- 没有本地存档时要在入口对应位置写“未获取副本”，不要创建不存在的链接。
- 信息来源应标明网站或来源名称(如 GitHub)，不得只写“来源”两个字。
- 信息来源没有网络地址时，直接在入口对应位置写来源定位信息。
- 示例只演示索引格式，不能作为实际分类或内容照抄。

## AGENTS.md

> `AGENTS.md` 是本目录给 Agent 使用的维护入口。只写当前目录长期有效的操作约束；
> 要做到即使 Agent 没有加载本规范，也应能仅凭该文件安全地整理和维护当前参考资料。

**参考示例：**

该示例为 `AGENTS.md` 的最低维护能力，必须逐章保留，不得删除、合并、改名或用其他章节中的零散内容代替；允许根据项目情况调整各章内部表述。

```md
## 给 Agent

> 项目 AGENTS.md 必须保留本章的条件规则，不得将其删除。

1. 本目录只存放用于查看、研究、比较、核验、举证、学习或借鉴的外部材料；项目自有成果、正式输入和交付内容不放在这里；
2. 先读同级目录的 [README.md](./README.md)，并只打开本次任务涉及的参考说明文件；
3. 禁止无差别读取全部项目，避免占用上下文。

## 新增参考

> 项目 AGENTS.md 必须保留本章的条件规则，不得将其删除。

1. 按实际用途选择分类；
2. 每个参考项单独建立文件夹，名称优先使用来源原名，不散放在参考目录根部；
3. 按要求在 `README.md` 对应分类中增加索引；
4. 写 `参考说明.md`：来源、固定版本或快照、核验日期、许可证、生命周期（`使用中`/`仅证据`/`已废弃`）、内容类型和实际参考范围。

## 拉取副本

> 项目 AGENTS.md 必须保留本章的条件规则，不得将其删除。

1. 先区分临时下载与长期副本；仅供本次查看的下载物放在临时目录，不作为参考副本入库；
2. 确有长期核验或反复使用价值时才保存本地存档，并按来源类型固定可复核的版本或快照；Git 项目记录固定提交，不跟随浮动分支；
3. 同一内容的原始文件和转换全文没有各自独立用途时，不得同时长期保留；
4. `参考说明.md` 补“本地存档”小节：位置、版本或快照、获取日期、用途、更新方式和入库策略；
5. 更新 `README.md` 的当前状态和实际分类说明；
6. 控制存储和上下文占用；不要为了“拉取”而拉取，也不要为了节约空间而放弃确有用途的副本。

## 更新副本

> 项目 AGENTS.md 必须保留本章的条件规则，不得将其删除。

触发条件（满足其一即可）：

1. 项目进入参考版本锁定或升级评估，需要对照新的固定版本或快照；
2. 来源发布与当前项目有关的重要修订或安全更新；
3. 参考说明记录的版本或快照与项目实际采用的参考依据不一致。

更新步骤：取得新的固定版本或快照 → 更新参考说明的版本、核验日期与受影响的结论 → 更新 `README.md` 的当前状态和实际分类说明 → 若结论影响项目正式文档，同步更新对应正文。

## 废弃原则

> 项目 AGENTS.md 必须保留本章的条件规则，不得将其删除。

1. 确认项目不再使用该参考项当前记录的用途、结论或版本；
2. 将`参考说明.md`的生命周期改为“已废弃”，记录日期、原因和最后参考的版本或快照；
3. 删除本地存档，保留参考项文件夹和参考说明；
4. `README.md` 中保留该参考项，在名称后标记“已废弃”；
5. `README.md` 入口中的本地存档改为“已删除”，继续保留参考说明和来源定位信息。

Agent 不得删除 `README.md` 中的参考项记录、来源链接或其他来源定位信息。本规范不提供删除这些记录的流程。

来源重新出现参考价值时，重新核验并更新参考说明；按需恢复本地存档，将生命周期改回“使用中”，再更新 README 的名称和入口。

## 状态约定

> 项目 AGENTS.md 必须保留本章的条件规则，不得将其删除。

1. 核验日期只表示所见事实，不构成跟随来源更新的义务；不触发更新条件就保持固定版本或快照。
2. 来源的版本、描述、数量和发布日期等信息可能变化，正式结论必须注明核验日期。

## 维护原则

> 项目 AGENTS.md 必须保留本章的条件规则，不得将其删除。

1. 不复制参考索引、动态数量、单项资料详情或整份治理规范，参考项的信息只在 `README.md` 维护。
2. 也不得把本次使用的命令、工具、脚本和临时选择写成长期要求。
3. 项目上级 `AGENTS.md` 只增加参考材料治理的触发条件和本文件链接，不得用本示例覆盖或重写。
4. Agent 有责任控制该文件大小，防止小窗口模型瞬间撑爆上下文，但仅限于删除重复内容、动态信息、单项资料详情和一次性操作步骤。

## 版本控制

> 项目 AGENTS.md 必须保留本章的条件规则，不得将其删除。

1. 项目尚未使用版本控制时，不代表本章不适用。
2. 项目尚未使用版本控制时，不得为了本规范自行初始化仓库。
3. 项目使用版本控制时，参考目录根部的 `README.md`、`AGENTS.md` 和 `CLAUDE.md` 属于项目治理文件，由本项目自己的仓库跟踪。
4. `参考说明.md` 放入来源仓库工作树时，必须写入该仓库的 `.git/info/exclude`；不得修改上游 `.gitignore`，也不得提交到来源仓库。
5. Git 参考项目可以直接放在参考项目录。来源仓库的 `.git` 只用于拉取、核验和更新来源版本，不属于本项目的版本控制。
6. Git 参考项目应固定在参考说明记录的提交，工作树不得残留临时修改、生成物或未排除的项目自有文件。
7. 未获用户明确要求，不得在来源仓库创建 commit、push、修改远端，也不得将其作为 submodule、gitlink 或普通项目文件提交到项目仓库。

## 维护结果验收

> 项目 AGENTS.md 必须保留本章的条件规则，不得将其删除。

每次新增、拉取、更新、废弃或调整本目录后，必须在向用户报告结果或结束任务前，重新读取实际文件并逐项验收。

**验收条目：**

1. 收录内容符合参考材料边界，没有混入项目自有成果、正式输入或交付内容。
2. 所有参考项都已分类，没有散落在参考目录根部。
3. 已废弃参考项仍保留参考说明、索引记录和来源定位信息。
4. 每个参考项都有参考说明，来源和实际参考范围可以重新核验。
5. 每段内容至少能帮助人类或 Agent 判断、定位、核验或维护资料；对两者都没有实际用途的内容已经删除。
6. 标题、层级和阅读顺序清楚，摘要与详细内容分开，读者无需加载与当前任务无关的长篇内容。
7. `README.md` 中的数量、分类、状态和链接与磁盘现状一致，项目内链接可以打开。
8. `README.md` 面向人类提供清楚的判断和查找入口，没有混入 Agent 操作步骤。
9. `README.md` 和 `AGENTS.md` 没有照抄规范，也没有把一次性命令、工具或临时选择写成长期规则。
10. `AGENTS.md` 和 `README.md` 是否存在无限膨胀的可能，如果存在询问用户如何处理。
11. `README.md` 和 `AGENTS.md` 能相互打开，双方各司其职，让未加载本规范的 Agent 仅凭该文件也能安全维护。
12. 确保版本控制制度，有序进行。
13. 确保没有机械生成的完整正文副本或无独立用途的重复格式以及大文件已记录按需读取方式。
14. 确保临时文件没有被索引或参考说明依赖，没有作为长期副本入库。
15. 确保每份长期副本都有实际用途，已保存的长期副本没有在临时目录留下重复文件，本次任务的抓取物已经处理完毕。
```

**维护原则：**

1. 如果已有 `AGENTS.md` 也必须按同一标准检查：保留有效的项目专用约束，补齐缺失内容。
2. 如果已有 `AGENTS.md`内容弱于示例时，只替换或补齐对应的薄弱部分，不得覆盖有效的项目专用约束。
3. 除此两种情况之外，参考示例中的所有章节必须全部保留，Agent 不得以任何理由任何借口删除示例中的章节。
4. 除非用户明确要求，或示例中的具体做法确实不适用于当前项目，那就只处理不适用部分，如果分不清，就问用户。

**再次重申：**新建/更新`AGENTS.md` 时，除上述特殊条件外，不得以任何理由删除示例中的内部章节。

 ## 本规范执行验收

执行验收时，必须重新读取本规范中的完整参考示例和最终 `AGENTS.md`，按示例中的内部章节逐项对照；不得凭记忆列出章节，也不得只检查最终文件。章节数量或名称不一致时，先补齐再结束任务。

## 冲突处理

1. 用户明确要求优先；
2. 项目已有的具体规范其次；
3. 已有合理结构和统一风格继续沿用；
4. 没有更具体要求时执行本规范。

冲突无法判断时，先向用户确认。
