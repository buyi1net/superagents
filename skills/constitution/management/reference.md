# 参考材料治理规范

> 把项目使用的外部参考材料分类保存，让用户和 Agent 能从一个入口知道有哪些材料、为什么保留、在哪里、当前是什么状态，并能继续维护。
>

## 收录边界

放入参考材料目录：

- 外部收集，只用于理解、研究、比较、核验、举证、学习或借鉴的材料；
- 外部项目、制度、标准、文献、数据、模板、方法、素材、案例和样例；
- 正式输入或外部组成部分的说明、快照和分析记录，只承担参考或证据职责时也可以收录。

不放入参考材料目录：

- 项目正在产出或长期维护的自有成果、过程记录、正式数据、交付内容和运行内容；
- 当前工作需要直接采用、编辑、加工、执行或随成果交付的正式输入与外部组成部分。

识别参考材料看用途，不看目录名称，也不看用户是否说出“参考材料”。

## 目录与分类

```text
<参考目录>/
├── README.md          # 路由与维护手册
└── <分类名称>/
    └── <参考项名>/
        ├── <说明文件>   # 如「参考说明.md」
        └── <本地副本，如有>
```

- 参考目录名称跟随项目语言和已有命名；中文可用“参考资料”，英文可用“reference”。
- 每个参考项单独建立文件夹，名称优先使用来源原名，不翻译。
- 每个参考项都必须分类，只有一个参考项也不能直接散放在参考目录根部。
- 分类名称按材料在当前项目中的实际用途确定，例如核心依据、流程范例、竞品项目、视觉参考和其它参考；这些名称只是示例，不是固定目录。
- 同类材料使用同一分类；跨类材料按主要用途归类，次要用途写入参考说明。
- 用不到的分类不创建，不预建空目录。
- 已有合理分类继续沿用。用户要求整理时可以按本规范重新分类；未获授权不得随意迁移或改名。

## 参考说明

每个参考项建立一份说明文件，与本地副本放在同一个参考项文件夹中。说明文件不要命名为 `README.md`，避免与外部项目自带的 README 冲突；中文项目可用“参考说明.md”。

参考说明记录：

- 来源名称；
- 来源定位信息；
- 固定版本或快照；
- 核验日期；
- 许可或版权；
- 生命周期；
- 内容类型；
- 实际参考范围；
- 本地副本的位置、获取日期和更新方式，如无副本则不写。

来源定位信息按实际情况填写完整 URL、DOI、ISBN、标准号、档案号、出版信息、内部位置、提供方或取得方式。有网络地址时使用可点击链接；没有网络地址时写出足以重新找到材料的信息，不得编造链接。

本地副本按固定版本或快照保存，不跟随浮动版本，也不写入项目自有内容。无法使用版本号或提交号的材料，记录可核验的快照日期或其他标识。

本地副本是否纳入项目正式存储，由许可条件、保存责任和项目存储方式决定；未纳入时使用项目的忽略或访问规则隔离，纳入时在参考说明中记录原因、范围和维护方式。

生命周期使用：

- `使用中`：当前仍作为参考依据；
- `仅证据`：只保留历史事实或结论依据；
- `已废弃`：当前不再使用，但说明和来源继续保留。

## 参考目录 README

`README.md` 是参考目录的统一入口，只写当前目录的实际内容和维护信息，不照抄本规范。

README 和参考说明应能快速阅读，只保留判断、定位、核验和维护所需的信息。长篇分析、大段摘录、实验过程和日志另存文件并从参考说明链接，不复制来源正文，也不要求读者一次加载全部内容。

README 应包含：

1. 本目录收录什么；
2. 阅读方法：先看索引中的“价值”，只打开与当前任务相关的参考说明和本地副本；
3. 当前状态：参考项数、分类数、本地副本数和最近核验日期；
4. 当前实际分类及其用途；
5. 按分类排列的参考索引；
6. 以后维护当前资料必须知道的实际约定。

维护约定必须结合当前目录编写，例如现有分类如何选择、本地副本怎样保存、更新时哪些记录需要一起修改、废弃时哪些信息必须保留。不得把本次拉取方式、临时选择或当前状态擅自写成长期规则。

每个参考项在索引中固定写三行：

```md
### 核心上游

- **cordis**
- **价值：**DSH 底层插件框架，第一方插件开发的编程载体。
- **入口：**[参考说明](核心上游/cordis/参考说明.md) · [本地副本](核心上游/cordis/)：`8cc9e33f` · 2026-08-14 · [GitHub](https://github.com/cordiverse/cordis)
```

- “价值”用一句话说明为什么保留，让读者不用打开说明文件也能判断是否相关。
- “入口”依次提供参考说明、本地副本和来源；项目内链接使用可点击的相对链接。
- 没有本地副本时写“本地副本：未获取”，不要创建不存在的链接。
- 来源没有网络地址时，直接写来源定位信息。
- 示例只演示索引格式，不能作为实际分类或内容照抄。

## 维护

### 新增

1. 按实际用途选择分类；
2. 建立参考项文件夹并写参考说明；
3. 按需获取固定版本或快照的本地副本；
4. 在 README 对应分类中增加三行索引；
5. 更新 README 的当前状态和实际分类说明。

### 获取或更新本地副本

1. 核验来源和实际需要参考的版本；
2. 根据材料类型选择获取方式，不预设浅克隆、完整克隆、下载或复制；
3. 把固定版本或快照放入参考项文件夹；
4. 更新参考说明中的版本、核验日期、本地位置和受影响结论；
5. 更新 README 入口中的版本或快照标识和获取日期；
6. 参考结论影响项目正式成果时，同步修改对应成果。

核验日期只表示当时确认的事实，不要求自动跟随来源更新。第三方描述、评分、数量和发布状态等动态信息必须同时记录核验日期。

### 废弃

1. 确认项目不再使用该参考项当前记录的用途、结论或版本；
2. 将参考说明的生命周期改为“已废弃”，记录日期、原因和最后参考的版本或快照；
3. 删除本地副本，保留参考项文件夹和参考说明；
4. README 中保留该参考项，在名称后标记“已废弃”；
5. README 入口中的本地副本改为“已删除”，继续保留参考说明和来源定位信息。

Agent 不得删除 README 中的参考项记录、来源链接或其他来源定位信息。本规范不提供删除这些记录的流程。

来源重新出现参考价值时，重新核验并更新参考说明；按需恢复本地副本，将生命周期改回“使用中”，再更新 README 的名称和入口。

## 输出前自查

报告完成、交付目录或结束任务前，重新读取实际文件并逐项检查。发现不符合先修正，未完成自查不得声称治理完成。

1. 收录内容符合参考材料边界，没有混入项目自有成果、正式输入或交付内容；
2. 所有参考项都已分类，没有散落在参考目录根部；
3. 每个参考项都有参考说明，来源和实际参考范围可以重新核验；
4. README 中的数量、分类、状态和链接与磁盘现状一致，项目内链接可以打开；
5. 本地副本与记录的固定版本或快照一致，内部没有混入项目自有内容；
6. 已废弃项目仍保留参考说明、索引记录和来源定位信息；
7. README 写的是当前资料的实际信息，没有照抄规范或把一次性做法写成长期规则；
8. 每段内容至少能帮助人类或 Agent 判断、定位、核验或维护资料；对两者都没有实际用途的内容已经删除；
9. 标题、层级和阅读顺序清楚，摘要与详细内容分开，读者无需加载与当前任务无关的长篇内容。

## 冲突处理

1. 用户明确要求优先；
2. 项目已有的具体规范其次；
3. 已有合理结构和统一风格继续沿用；
4. 没有更具体要求时执行本规范。

冲突无法判断时，先向用户确认。
