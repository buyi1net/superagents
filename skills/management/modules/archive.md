> 本规范管理已经退出当前流程、但仍需长期保留以便追溯的内容。判断依据是内容职责，不是目录是否恰好命名为 `archive/`；既有项目可以沿用已经稳定使用的归档位置。

仅在首次建立归档场景、现有归档治理存在具体缺口，或用户明确要求整理、迁移和审计时使用本规范。已经能够自治的归档区日常维护直接执行项目内规则，不用本规范反复对照。

## 收录边界

归档内容包括已废弃的旧版本、旧方案和阶段成果。归档后默认只读，不参与当前源码、构建、测试或运行。

以下内容不得归档：

- 当前仍在开发、构建、测试或运行所需的内容；
- 临时备份、实时日志和未完成材料；
- 仍被当前流程作为依赖或唯一来源的文件。

## 解锁顺序

1. 先确认内容已经退出当前流程、归档位置和恢复用途；仍在使用或无法判断的内容不得移动到归档区。
2. 首次使用归档区时，依次完成以下入口：使用文件复制操作从[标准底稿](./templates/archive-agents.md)建立 `AGENTS.md`，建立固定的 `CLAUDE.md`，建立只描述当前实际内容的一级 README。重新读取三份文件并更新直接上级索引后，归档区才解锁。
3. 既有归档区先读取一级 README、`AGENTS.md` 和目标归档记录，确认位置、命名和恢复边界后再处理归档项；入口缺失或相互冲突时只修复入口。
4. 在实际归档前读取当前本地时间并确定名称。不得预估、取整或事后改写归档时间。
5. 归档项实际存在后，立即把它加入归档索引并补齐归档记录；完成记录前不得继续处理下一项归档工作。
6. 恢复归档内容前先确认兼容性和恢复位置，恢复到临时副本或明确目标，不得直接覆盖当前内容。

## 组织和命名

- 归档项可以使用版本化目录或 `.zip`。需要整体分发、冻结或长期只读保存时使用 `.zip`；只有一个文件的归档项可以保留原格式。
- 归档包或归档文件使用 `名称-版本-YYYYMMDD-HHmm` 命名；时间使用执行归档时的本地时间，压缩归档的完整名称以 `.zip` 结尾。
- 不为每个归档目录机械新增 README。归档入口由归档区一级说明或已有统一索引承担。

## 归档记录

README 的当前归档索引只记录实际存在的归档项。统一记录文件可以保留已经删除的历史记录，但必须单独标记为“已删除”，不得继续显示为当前可用归档。每项记录包含以下信息：

- 名称、版本和归档时间；
- 归档用途和原因；
- 被替代的方案或版本以及替代决策；
- 当前是否仍可恢复。

恢复归档内容前先确认它与当前结构、依赖和规则是否兼容，不得直接覆盖当前内容。

## 删除归档

- 删除归档内容属于破坏性操作，只有用户明确要求或项目已有明确流程时才能执行。
- 删除前确认归档项不参与当前流程、不是唯一来源，并确定需要保留的归档记录和来源定位。
- 删除实体后立即更新归档索引，记录删除对象、时间、原因和替代定位。用户明确要求连记录一并清除时，按用户指定范围执行。

## AGENTS.md

1. 归档区的 `AGENTS.md` 是后续 Agent 的直接维护入口。新建时必须直接复制[标准底稿](./templates/archive-agents.md)的完整内容，再根据项目实际位置、命名和记录方式精准修改；不得凭记忆或整段生成重建。
2. 已有 `AGENTS.md` 时，先判断空上下文 Agent 能否仅凭项目内入口安全地归档、恢复和删除内容；能够做到就保留原结构，不与标准底稿逐章比较。
3. 已有入口存在具体缺口时只补缺失能力。只有用户明确要求迁移到标准制度时，才使用标准底稿重构并保留其中全部 `##` 章节和顺序。
4. 项目化调整完成后，不得把本规范或外部 skill 作为归档区能够继续维护的唯一依据。

## 验收

1. `README.md`、`AGENTS.md`、`CLAUDE.md` 均已存在并能互相打开；新建入口或明确迁移到标准制度时，最终 `AGENTS.md` 保留标准底稿中的全部 `##` 章节和顺序；
2. 归档区入口早于本次新增的首个归档项，归档项存在、恢复或删除后立即完成了索引和记录；
3. 名称和记录中的版本、时间与实际归档时点一致，没有使用预计时间；
4. 归档内容不参与当前源码、构建、测试、运行或交付，也不是当前流程的唯一来源；
5. 索引与实际归档项一致，恢复条件能够执行且不会直接覆盖当前内容，删除具有明确依据并保留了要求的追溯信息；
6. 新建入口或明确迁移到标准制度时，实际执行过“重新读取底稿 → 文件复制 → 精准修改 → 最终对照”；修复已有入口时有具体缺口依据，没有机械套用模板。
