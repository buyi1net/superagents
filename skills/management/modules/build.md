> 本规范管理已经确认可直接分发、加载、部署、运行或交接的最终交付物。判断依据是内容生命周期，不是目录是否恰好命名为 `build/`；构建暂存、半成品和待验证包不属于最终交付物。

## 解锁顺序

1. 构建前先在项目 README 或开发侧交付说明中确认交付类型、对象、范围和源码边界。
2. 构建暂存区和最终交付区分别解锁：先按临时内容规范建立或核验暂存区入口，再建立或核验最终交付区 README，并立即更新各自的直接上级索引。一个区域已解锁不能替代另一个区域。
3. 只在已解锁的构建暂存区组装文件，生成逻辑清单并完成初步检查；不得直接向最终交付目录边开发边验证。
4. 在暂存副本、解压副本或其它已确认的临时副本中完成运行和交付验证，清理运行副作用并确认待交付清单不含运行生成物。
5. 验证通过后，才把同一份逻辑清单写入最终交付目录和压缩包，并立即更新最终交付区 README。
6. 最终交付物形成后如又发生运行、修改、重建或补文件，先前验证立即失效，必须重新执行清单、哈希、运行副作用和原件未变检查。

最终交付物存在不能证明构建暂存、验证和晋级顺序正确；先写入最终区再补验证属于违规。

## 交付边界

- 最终交付区只保存已经确认可交付的目录、发布包、安装包、部署包，以及与其对应的使用说明、更新日志和校验文件。
- 开发项目根、构建暂存根、交付包根和运行实例根分别管理，不得让同一目录同时承担相互冲突的生命周期。
- 开发侧交付说明属于长期项目文档；构建暂存统一放入临时区的 `build/` 分类，不得在最终交付区内暂存或直接开发。
- 单一且规模较小的项目可以使用 `build/<项目>-<版本>/`；只有存在多个交付类型或发布渠道时，才增加有实际内容的分类层级。

## 交付说明

构建前必须在项目 README 或开发侧交付说明中明确交付类型、面向对象、包含范围以及是否包含完整源码、测试和开发脚本。

每种最终交付物必须有对应的使用说明、更新日志和校验信息，并说明：

- 交付类型和适用环境；
- 使用入口、运行方式和验证命令；
- 是否包含完整源码。

交付物内部的说明只描述当前交付内容，不复制开发项目根说明，也不得索引交付包中不存在的开发目录或项目外路径。

## 组装和验证

- 交付目录和 ZIP 同时存在时，二者必须来自同一份逻辑文件清单。
- 待打包目录、半成品和待验证目录留在构建暂存区，不得出现在最终交付区。
- 最终交付目录和压缩包不得在其中直接开发或修改。需要运行验证时，在解压副本或临时副本中执行；验证后复查原交付物没有被运行过程改变。
- `__pycache__`、运行数据库、日志、截图、缓存、锁、进程文件、上传文件和其他运行时生成内容不得进入构建暂存或初始交付包。
- 最终交付物应能根据同一份源码和构建脚本整体删除后重建，不得保存开发侧唯一源文件。
- 启动交付副本或外部程序时，记录本次创建的准确进程、端口和临时位置，只清理这些目标。不得用按程序名称结束全部进程的方式代替精确清理。

## 验收

1. 开发侧交付说明、暂存区入口和最终交付区入口均早于对应区域的主体内容；
2. 交付物能够确认经过“暂存组装 → 副本验证 → 最终晋级”，没有先在最终区运行或修改；
3. 目录与 ZIP 来自同一逻辑清单，逐文件一致，校验文件行尾和路径格式可由目标环境实际校验；
4. 最后一次影响交付内容的操作之后重新完成了全部验证，最终目录没有缓存、数据、日志、截图或其它运行生成物；
5. 项目外进程、端口和临时资源按准确目标清理，没有影响本任务之外的同名程序或用户环境。
