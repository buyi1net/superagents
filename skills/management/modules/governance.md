> 本规范只用于用户明确要求整理、规范、治理、审计、重构、迁移项目结构或规则，或者评估项目能否长期维护的场景。普通文件操作、局部修改和已有制度下的日常维护不得自行扩大到本规范。

## 治理范围

1. 先确认用户指定的项目、目录、内容类型和允许改变的范围；“整理一个目录”不授权重构整个项目。
2. 治理对象是项目的维护能力，不是让目录名称、章节结构或规则写法与 `management` 完全一致。
3. 用户只要求评估时保持只读，输出具体缺口和影响；只有用户要求修改或任务本身明确包含整改时才写入。

## 现状优先

1. 先读项目根和目标范围最近的 Agent 入口、README、索引、脚本、配置及直接相关说明，再检查磁盘；不得先套模板再寻找理由。
2. 对每项现有制度分别标记：继续沿用、存在具体缺口、已经失效或相互冲突。不同于本 skill 不是缺口。
3. 能让空上下文 Agent 安全完成对应维护的现有制度继续沿用，不迁移目录、不统一命名、不改写入口结构。
4. 只有缺少必要能力时才读取对应场景模块；不得为了完整比较而加载所有场景规范。

## 自治审计

使用一个没有加载本 skill、没有项目历史和前序对话的 Agent 视角，逐项检查：

1. 能否从项目根确认项目边界、当前实际内容和目标场景入口；
2. 能否只读取当前任务所需规则，不需要无差别扫描项目；
3. 能否在创建、下载、生成、修改、移动或运行内容前确定归属、生命周期、正确位置和维护顺序；
4. 能否在结构或职责变化后立即找到并更新直接上级入口；
5. 能否区分正式内容、外部参考、源码、测试、运行数据、生成物、临时物、归档物和最终交付物；
6. 能否在不依赖本机缓存、外部 skill、绝对路径、当前 Agent 记忆或一次性命令的情况下继续维护；
7. 能否从项目内稳定入口识别破坏性操作、外部副作用和需要用户授权的边界。

## 整改顺序

1. 按实际缺口选择最小整改范围；新场景或缺少完整治理的场景，完整读取对应模块。
2. 先确定每项规则的唯一职责和项目内正式位置，再建立或修改入口；详细正文不得集中堆入项目根 `AGENTS.md`。
3. 已有内容先完整保留并辨别有效部分。精准补齐缺失能力，链接到项目内稳定位置；除非用户明确要求制度迁移，不使用标准模板整体重塑已有入口。
4. 先让入口和规则成立，再移动、分类或修改主体内容；每次结构、职责、入口或索引变化后立即维护直接上级。
5. 项目内落地的规则必须自包含。可以补充外部 skill 作为增强，但不得让它成为项目能够继续维护的唯一依据。

## 验收

1. 所有改动都位于用户授权范围内，没有把局部整理扩大为全项目改造；
2. 每项调整都有具体治理缺口作为依据，不是因为现有结构与模板不同；
3. 项目根入口只保留边界、触发条件、最小红线和稳定路由，详细场景规则位于职责明确的项目内文件；
4. 原有有效规则、说明、链接和项目专用约束没有在迁移中丢失；
5. 以空上下文、未加载本 skill 的 Agent 视角复核后，能够从项目根找到目标场景并独立完成同类维护；
6. 索引、入口、说明、脚本、配置和最终磁盘一致，不存在只在本次会话中成立的隐含规则。
