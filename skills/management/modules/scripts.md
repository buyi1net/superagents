> 本规范管理可重复执行的构建、测试、部署、迁移、校验和数据处理脚本。判断依据是内容职责，不是目录是否恰好命名为 `scripts/`；既有项目可以沿用工具链已经确定的脚本位置。

仅在首次建立脚本场景、现有脚本治理存在具体缺口，或用户明确要求整理、迁移和审计时使用本规范。已经能够自治的脚本区日常维护直接执行项目内规则，不用本规范反复对照。

## 收录边界

脚本区只保存可重复执行的自动化脚本。以下内容不属于脚本区：

- 业务源码；
- 正式测试；
- 不可重复的一次性实验脚本。

一次性实验脚本属于临时内容；如果实验结果转为长期流程，应先整理输入、输出、副作用和前置条件，再纳入正式脚本区。

## 解锁顺序

1. 首次使用脚本区时，先建立脚本区一级 README，写明边界和当前实际内容，再更新直接上级索引。不得先创建脚本或分类目录，再补说明。
2. 既有脚本区先读取一级 README 和目标脚本说明，确认用途、输入、输出、前置条件和副作用后再修改或执行。
3. 新脚本实际创建后，立即更新脚本区 README；只有出现两个及以上独立用途时，才建立有实际内容的分类目录。
4. 首次执行脚本前，先确认全部输出位置已经按对应规范解锁，并在说明中记录项目内外副作用和清理责任。不得先运行再根据生成结果决定归属。
5. 启动进程、服务或外部程序时记录本次产生的准确标识，只清理本次目标；不得按程序名称、模糊路径或宽泛匹配结束其它同名资源。

## 分类和入口

- 脚本按操作用途归类，例如 `runtime/`、`test/`、`build/`、`data/`、`deploy/`。
- 存在两个及以上独立用途时，建立有实际内容的二级分类目录。
- 根部只保留目录说明文件、必要的 Agent 入口和实际存在的用途分类目录。
- 只有一个脚本且没有分类价值时，才可以直接放在根部，并在一级目录说明中写明理由和运行方式。

## 使用说明

可重复脚本必须在脚本区 README、已有索引或项目长期文档中说明：

- 输入和输出；
- 前置条件和运行方式；
- 对项目内外文件、进程、服务、环境或数据的副作用。

脚本不得隐藏未声明的外部写入、安装、删除或数据修改行为。

## Agent 入口

脚本区默认继承最近的上级 `AGENTS.md`，不得仅因建立脚本目录就机械新增局部入口。README、脚本帮助信息和脚本自身应先承担项目实际输入、输出、运行方式和副作用说明。

满足以下任一条件时，脚本区形成独立治理边界，必须在首次执行对应高风险操作前按 Agent 入口治理建立或核验局部 `AGENTS.md` 和 `CLAUDE.md`：

- 脚本区经常作为独立工作区交给 Agent 维护；
- 存在部署、迁移、删除、安装或修改项目外数据和环境的脚本；
- 多类脚本具有不同权限、运行环境或清理责任，上级入口无法清楚路由；
- 已经发生过 Agent 未读取脚本说明、扩大副作用或错误清理的问题。

局部入口只写脚本区长期有效的操作门禁和读取条件，不复制每个脚本的动态参数与说明。

## 项目内自治

首次建立或修复脚本场景时，项目根入口和脚本区 README 必须让空上下文 Agent 找到脚本分类、运行说明以及每个脚本的输入、输出、前置条件和副作用。高风险脚本的授权、清理和失败边界必须进入项目内局部入口或可执行检查；不得只把这些要求留在本规范中。

## 验收

1. 脚本区 README 早于本次首个脚本，脚本或分类实际出现后立即完成了索引维护；
2. 每个脚本的输入、输出、前置条件、运行方式和项目内外副作用都有直接说明；
3. 实际输出位置与执行前声明一致，没有依赖事后搬运或整理；
4. 清理只影响本次脚本创建的准确文件、目录、进程、服务和端口。
5. 没有加载本规范的 Agent 能从项目根找到脚本场景，并仅凭项目内入口安全地执行和维护对应脚本。
