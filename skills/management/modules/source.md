> 本规范管理项目自有的正式源码、可维护技术包和独立交付单元。判断依据是内容职责，不是目录是否恰好命名为 `source/`；既有项目可以保留已经稳定使用的源码根。

仅在首次建立源码场景、现有源码治理存在具体缺口，或用户明确要求整理、迁移和审计时使用本规范。已经能够自治的源码区日常维护直接执行项目内规则，不用本规范反复对照。

## 收录边界

源码区是项目实现的主要维护来源。以下内容不属于源码区：

- 完整外部上游项目和参考副本；
- 运行数据和临时文件；
- `target/`、`node_modules/`、`out/`、`dist/` 等可以由工具链重新产生的目录。

工具链生成目录可以按工具要求出现在源码树中，但必须可重建，并纳入忽略规则或上级说明。

## 解锁顺序

1. 首次使用源码区时，先建立源码区一级 README，写明边界和当前实际直接内容，再更新项目根索引。不得把 README 与首批源码、单元测试、项目目录或工具生成目录并行创建。
2. 既有源码区先读取一级 README 和目标子项目的直接入口，确认源码根、独立交付单元和现有运行测试方式后再修改。
3. 源码区入口只解锁源码区。新建的独立子项目本身构成项目根时，必须再按主文件建立该子项目入口，不能用源码区 README 代替。
4. 创建首个子项目或重要技术包后，立即更新源码区 README；完成索引维护后才继续写实现文件。
5. 单元测试随对应源码单元维护；工具将在源码树产生缓存、依赖或构建目录时，执行前先声明位置、重建方式和忽略规则。

## 项目组织

- 新建项目的正式源码默认位于 `source/` 下；一个独立交付单元通常使用 `source/<项目>/`，多个可独立构建或部署的单元可以使用 `source/<类别>/<项目>/`。
- 既有项目保留已经稳定使用的源码根。除非任务明确要求迁移，并完成构建、测试和入口验证，否则不得为了套用默认目录而搬动源码。
- 多个项目或独立交付单元不得共用没有职责边界的源码目录。

## 源码区总览

源码区必须有一级目录总览说明，即使只有一个子项目也不能省略。总览应说明：

- 源码区的职责和边界；
- 当前实际存在的直接子项目；
- 每个子项目的主要职责和主要入口；
- 适用的运行和测试方式。

总览只描述直接子项目、公开入口和职责边界，不逐个解释实现文件、函数和类，也不维护完整文件清单。直接子项目、重要技术包或大型拆分单元需要额外说明时，使用源码区 README、项目长期文档或已有索引，不机械创建深层目录说明。

源码区默认继承最近的上级 `AGENTS.md`，不得仅因建立源码目录、技术包或模块就机械新增局部入口。独立子项目本身构成项目根、用户或既有项目已经规定入口，或者真实架构边界需要不同规则时，才按 Agent 入口治理处理；编码方法、语言规范和框架实践不写入本模块，由开发规范、项目工具链和专门的开发 skill 承担。

## 项目内自治

首次建立或修复源码场景时，项目根入口和源码区 README 必须让空上下文 Agent 找到源码根、直接子项目、职责、运行入口、测试方式和生成物边界。独立子项目形成新的项目根或具有不同维护规则时，在该边界建立项目内入口；不得把本规范或外部开发 skill 作为识别源码结构和项目命令的唯一依据。

## 验收

1. 源码区 README 早于本次首份源码、单元测试或子项目内容，新增直接子项目后立即完成了总览维护；
2. 源码、外部参考副本、运行数据、临时文件和构建生成物边界清楚；
3. 每个直接子项目或独立交付单元都有可定位的职责、运行入口和测试方式；
4. 工具生成目录可重建并已纳入忽略或上级说明，没有成为唯一正式成果。
5. 没有加载本规范的 Agent 能从项目根找到源码场景，并仅凭项目内入口定位项目命令和正确维护边界。
