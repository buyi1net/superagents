> 本规范管理跨子项目或跨模块的集成、端到端、回归、验收测试和公共测试数据。判断依据是测试范围，不是目录是否恰好命名为 `tests/`；既有项目可以沿用工具链已经确定的测试位置。

## 测试边界

- 只验证单个模块且不启动真实服务的单元测试，保留在对应源码单元内。
- 启动真实服务、访问真实 HTTP/API、跨模块验证完整流程或面向交付验收的测试，属于项目级测试。
- 可版本管理、可重复使用的测试基线和公共测试数据属于正式测试内容；一次性测试数据库、演示数据、日志、截图、缓存和运行副本属于临时内容。
- 面向用户验收的集成测试可以随源码交接包提供；开发期单元测试默认留在开发项目，不因“完整”而全部复制进运行交付包。

## 解锁顺序

1. 首次使用项目级测试区时，先建立测试区一级 README，写清边界、当前实际分类、运行命令、数据、端口、服务依赖、产物位置和清理规则，再更新直接上级索引。不得把 README 与首份测试并行创建。
2. 既有测试区先读取一级 README 和目标测试入口，确认测试性质、正式基线与一次性产物边界后再修改或运行。
3. 新测试或新分类实际创建后，立即更新测试区 README；不预建没有测试内容的分类。
4. 首次运行测试前，先按临时内容规范确定一次性数据、日志、截图、浏览器配置和运行副本的位置，并记录本次服务、端口和进程的准确标识。
5. 测试完成后只停止本次启动的准确进程和服务，释放本次端口并清理本次临时资源；不得按程序名称结束全部同名进程。
6. 清理改变测试区或临时区当前内容后，立即更新对应 README，再进入交付或最终验收。

## 分类和入口

- 项目级测试按测试性质分为实际存在的分类，例如 `integration/`、`e2e/`、`regression/`、`acceptance/`。
- 只有一个测试类别且规模很小时，才可以在根部直接放测试文件，并在测试区一级目录说明中写明理由。
- 不预建没有测试内容的分类目录。

## 测试区说明

测试区一级目录说明必须写清：

- 测试区边界和当前实际分类；
- 运行命令；
- 测试数据、端口和服务依赖；
- 测试产物位置；
- 临时资源的清理规则和正式证据的保留规则。

某项没有对应内容时明确写“无”，不能只依赖项目根说明或测试脚本中的注释。

## Agent 入口

测试区默认继承最近的上级 `AGENTS.md`，不得仅因建立测试目录就机械新增局部入口。测试区 README、测试框架配置和可重复执行的测试脚本应先承担项目实际命令、依赖、产物和清理说明。

满足以下任一条件时，测试区形成独立治理边界，必须在首次运行对应测试前按 Agent 入口治理建立或核验局部 `AGENTS.md` 和 `CLAUDE.md`：

- 测试区经常作为独立工作区交给 Agent 维护；
- 测试会连接真实服务、修改外部数据、占用固定基础设施或产生需要长期保留的正式证据；
- 多套测试具有不同环境、权限、数据或清理责任，上级入口无法清楚路由；
- 已经发生过 Agent 混淆正式基线与一次性产物、遗留服务或扩大清理范围的问题。

局部入口只写测试区长期有效的运行门禁和读取条件，不复制每个测试用例、实时端口或单次运行状态。

## 验收

1. 测试区 README 早于本次首份项目级测试，新增分类后立即完成了索引维护；
2. 单元测试、项目级测试、正式基线和一次性产物按职责分开；
3. 实际测试命令、数据、端口、服务依赖、产物位置和清理行为与 README 一致；
4. 测试结束后，本次服务和端口已释放，本次临时资源已清理或明确保留，未影响其它同名进程和用户环境；
5. 测试通过只能证明被测结果，不能替代测试区、临时区或交付区此前应完成的解锁顺序。
